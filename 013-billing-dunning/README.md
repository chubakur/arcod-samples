# 013 — Billing & dunning (подписки и повторные списания)

Учебная, но честная биллинговая система: план из прайс-листа, подписка,
счёт, попытка списания через внешний платёжный шлюз, чек в S3, политика
повторных попыток (dunning) и парковка подписки в `past_due`, когда карта
окончательно мертва.

Фишка проекта — деньги не списываются в HTTP-запросе. `POST /v1/subscriptions`
пишет подписку и первый счёт в MySQL, кладёт задание в очередь и сразу
отвечает. Дальше работают два фоновых консьюмера:

1. `charge` — снимает деньги через внешний шлюз, кладёт чек в S3, продлевает
   период подписки;
2. `dunning` — решает, что делать с отказом: перевооружить списание (до трёх
   попыток) или перевести подписку в `past_due`.

## Схема

```
                POST /v1/subscriptions
                        |
                        v
   +---------------------+          +----------------------+
   |  Billing (Arc)      |  insert  |  MySQL               |
   |  plan/subscription  +--------->|  Plan / Subscription |
   |  invoice            |          |  Invoice / outbox    |
   +----------+----------+          +----------------------+
              | publish "charge"
              v
        +-----------+   at-least-once    +--------------------------+
        |  Redis    |------------------->| consumer: charge         |
        |  queue    |                    |  kv.seen idempotency     |
        +-----------+                    |  HTTP -> payment gateway |
              ^                          +----+---------------------+
              | publish "dunning"             | blobPut
              |                               v
        +-----+-----------+            +-------------+
        | consumer:       |            |  MinIO/S3   |
        | dunning         |            |  receipts/  |
        | retry or park   |            +-------------+
        +-----------------+
```

Состояния:

- счёт: `pending → retrying → paid` либо `pending → retrying → failed`;
- подписка: `active → past_due` (после трёх отказов), `past_due → active`
  после успешной ручной оплаты (`POST /v1/invoices/:id/pay`).

## Компонент → provider

| Компонент | Возможность | Provider | Где живёт |
|-----------|-------------|----------|-----------|
| `store` — планы, подписки, счета | `sql` | `mysql:8.4` | контейнер `db` |
| `locks` — идемпотентность списаний | `kv` | `mysql:8.4` | таблица `arcod_kv` в `db` |
| `events` — задания `charge`/`dunning` | `queue` | `redis:7-alpine` | контейнер `queue` |
| `files` — чеки | `blob` | `minio` (S3) | контейнер `s3` |
| `uuid` | `ids` | `local` | процесс сервиса |
| `Gateway` — платёжный шлюз | `endpoint` | HTTP-мок | `mock/gateway.mjs`, порт 9099 |

Четыре внешние системы: MySQL (в ней же таблица `arcod_kv` для
идемпотентности), Redis (очередь), S3-совместимое хранилище, платёжный
шлюз. Четыре провайдера, два фоновых консьюмера.

## API

| Метод и путь | Что делает |
|--------------|------------|
| `POST /v1/plans` | добавить план: `code, name, priceCents, intervalDays` |
| `GET /v1/plans` | прайс-лист |
| `POST /v1/subscriptions` | подписка: `planCode, customer, email, cardToken`; создаёт счёт и ставит `charge` в очередь |
| `GET /v1/subscriptions/:id` | подписка и её состояние |
| `GET /v1/subscriptions/:id/invoices` | счета подписки |
| `GET /v1/invoices/:id` | счёт (`status`, `attempts`, `lastError`) |
| `POST /v1/invoices/:id/pay` | ручная повторная попытка (409, если уже оплачен) |
| `GET /v1/invoices/:id/receipt` | чек из S3 (JSON) |
| `POST /v1/admin/reconcile` | вернуть зависшие `retrying`-счета в очередь |
| `POST /v1/admin/renew` | продлить подписки с истёкшим периодом (эмуляция планировщика) |
| `GET /v1/stats` | active / pastDue / collectedCents / failedCents |
| `GET /healthz` | сервис + MySQL + Redis + S3 |

## Идемпотентность

Очередь at-least-once, поэтому `charge` помнит ключ `charge:<invoice>:<attempt>`
через `locks.seen`. Повторная доставка того же сообщения не звонит в шлюз;
шлюз, в свою очередь, тоже дедуплицирует по `idempotencyKey`. В smoke-тесте
проверяется, что на один счёт приходится ровно один вызов шлюза.

## Запуск

```bash
arcod check
arcod build --impl --port 8099
./smoke.sh            # поднимает compose, мок шлюза, гоняет сценарии, печатает PASS
arcod run --down --impl
```

Сервис — `http://localhost:8099`, мок шлюза — `http://localhost:9099`.
Smoke-сценарий: план → подписка (`tok_ok`) → счёт оплачен, чек в S3 →
ровно один вызов шлюза → `tok_flaky` (первый отказ, второй успех) →
`tok_dead` (три отказа, счёт `failed`, подписка `past_due`) → статистика →
повторная оплата оплаченного счёта даёт 409.

## Опыт использования Arc

Что понравилось:

- `job` + `on: events.charge` — консьюмер описан в модели теми же
  `effects`, что и HTTP-операции; из спеки видно, что фоновая работа не
  имеет доступа к сети напрямую.
- `effects` действительно дисциплинируют: `charge` не может незаметно
  прочитать план из БД — пришлось хранить `intervalDays` в подписке, потому
  что `store.find` не был объявлен. Это ровно та ошибка, которую хочется
  поймать на ревью.
- `locks.seen` + at-least-once очередь дают идемпотентность без отдельной
  таблицы ключей; для платёжной системы это главное.

Чего не хватило:

1. **Планировщика/отложенных сообщений.** Dunning-политика в реальности —
   это «через 1 день, через 3 дня, через 7 дней». В Arc нет ни `delay` у
   `queuePublish`, ни таймеров уровня сервиса (таймеры есть только в
   workflow-движке 008). Поэтому повторные попытки идут сразу, а продление
   периода вынесено в ручной `POST /v1/admin/renew`. Нужен либо
   `events.publishLater(topic, payload, delay)`, либо `cron`-блок в сервисе.
2. **Единая область видимости тел операций.** Все `impl/*.mjs` склеиваются в
   один модуль: две константы `MAX_ATTEMPTS` в разных файлах ломают сборку
   (`duplicate top-level name`). Пришлось переименовать в
   `DUNNING_MAX_ATTEMPTS`. Хотелось бы тело в своей области видимости.
3. **`io.remote` возвращает конверт** `{status, body}` (issue #32): в
   примере есть защитное `reply.body ?? reply`, но в README аркада об этом
   не сказано.
4. **Нет способа выразить «сумма по выборке»** — `store.count` считает
   строки, `collectedCents` приходится складывать в теле, вычитывая до 1000
   счетов. Для отчётности просится `store.aggregate` или `olap`.
5. W012: у каждой операции предупреждение «no examples», пока не напишешь
   `examples { ... }`. Примеры полезны, но шумят в каждой сборке.

## Ограничения демо

- Налоги, скидки, proration при смене плана и возвраты не реализованы.
- `renew` не создаёт счета для `past_due`-подписок: они ждут ручной оплаты.
- Шлюз — мок: `tok_ok` всегда успех, `tok_flaky` отказывает один раз,
  `tok_dead` отказывает всегда.
