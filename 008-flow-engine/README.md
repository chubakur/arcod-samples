# 008 — Flow engine

Долговечный движок workflow, у которого **определения приходят данными, а не
синтаксисом**. Клиент описывает шаги (action, зависимости, задержки, ретраи,
компенсации) и создаёт запуски; движок хранит состояние каждого шага, сам
решает, что готово, держит таймеры в `nextAt` и разворачивает компенсации в
обратном порядке.

Это backend-пример: HTTP API, модель, Redis и e2e-проверка. UI нет.

## Зачем ещё один workflow

В Arcod уже есть `workflow` и `saga`: шаги и компенсации описываются в
контракте и компилируются. Это правильно для *своего* пайплайна — отчёты,
ночная сборка, checkout. Но не для *чужого*: если граф приходит из админки,
из тикета или из JSON клиента, компилятор про него ничего не знает. Нужен
интерпретатор: состояние — записи, переходы — код, а контракт описывает только
API и эффекты.

Отсюда три вещи, которых нет у статического workflow:

- **Запуск — это запись.** Можно перечислить, отменить, показать историю шагов.
- **Шаг — это запись.** Видно `attempts`, `dueAt`, `error`; ретрай не теряется
  между запросами.
- **Время — это поле.** `nextAt` переживает перезапуск сервиса, потому что
  лежит в Redis, а не в таймере процесса.

## Модель

| Сущность | Ключ | Что хранит |
|---|---|---|
| `WorkflowRec` | имя | версия, JSON-граф шагов, дата |
| `RunRec` | uuid | статус, вход, переменные, поколение, `nextAt` |
| `StepState` | `runId:step` | статус шага, попытки, `dueAt`, вывод, ошибка |
| `Claim` | `runId:generation` | кто и когда забрал запуск на тик |
| `ScheduleRec` | имя | период и следующий запуск |

Шаг:

```json
{
  "name": "charge",
  "action": "flaky",
  "after": "validate",
  "key": "",
  "value": "charged",
  "delayMs": 0,
  "retry": 2,
  "backoffMs": 200,
  "failFirst": 1,
  "compensate": "refund"
}
```

Действия намеренно маленькие: движок не вызывает чужие сервисы (для этого нет
`remote` в эффектах). `ok`, `set`, `flaky`, `fail`, `sleep` — достаточно, чтобы
проверить переходы, ретраи, таймеры и откат.

Состояния запуска: `pending → running → done | failed | cancelled`.
Состояния шага: `pending → waiting → done | failed`, плюс `skipped` у
компенсации без действия.

### Что делает тик

1. Находит созревшие расписания и создаёт по запуску на период.
2. Берёт запуски `pending`/`running`, у которых `nextAt <= now`.
3. На каждый запуск вставляет `Claim { runId, generation }`. `unique Claim.slot`
   — единственная атомарная операция, доступная телу: вставка либо выигрывает,
   либо бросает `Conflict`. Второй тик с тем же поколением не пройдёт.
4. Прогоняет одну волну: готовые шаги выполняются, шаг с `delayMs` уходит в
   `waiting` с `dueAt`, упавший шаг — в `waiting` с экспоненциальным бэкоффом
   или в `failed` после исчерпания `retry`.
5. Если шаг упал насовсем — компенсации выполненных шагов в обратном порядке,
   статус `failed`. Если всё готово — `done`. Иначе — новый `nextAt` и
   `generation + 1`.

Тик — это HTTP-вызов `POST /v1/ticks`. Часы живут снаружи: сервис не обещает
их точность и не запускает фоновый цикл. Это ограничение платформы, а не
дизайна (см. «Опыт»).

## API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/v1/workflows` | принять определение (`Invalid`, `Conflict`) |
| `GET` | `/v1/workflows` | список определений |
| `GET` | `/v1/workflows/{name}` | одно определение |
| `POST` | `/v1/runs` | создать запуск, `input` подставляется в `{{input}}` |
| `GET` | `/v1/runs?status=&limit=` | страница запусков (курсор) |
| `GET` | `/v1/runs/{id}` | запуск со всеми шагами |
| `POST` | `/v1/runs/{id}/cancel` | откатить и закрыть (`Conflict` для терминальных) |
| `POST` | `/v1/ticks` | продвинуть всё, что созрело |
| `POST` | `/v1/schedules` | периодический запуск |
| `GET` | `/v1/schedules` | список расписаний |
| `GET` | `/v1/health` | `{ok, workflows, runs}` |

`{{vars.name}}` и `{{input}}` разворачиваются в `value` у действий `ok`/`set`.

Все POST отвечают `201`, включая `cancel` и `tick`: генератор берёт код из
объявления операции, а не из семантики. Для клиента это значит «смотри на тело,
не на код».

## Запуск

```bash
arcod check
arcod build --impl
arcod run --impl --port 8091
./smoke.sh                 # сборка, стек, HTTP-сценарии, PASS
arcod run --down --impl    # остановить
```

`smoke.sh` проходит: валидацию графа (цикл, неизвестное действие), ретрай с
бэкоффом, таймер шага, переменные запуска, компенсацию в обратном порядке,
отмену, расписание с периодом 1 с, гонку двух тиков за один claim и края
400/404.

Стек — Redis, порт по умолчанию `8091` (переопределяется `PORT`).

## Опыт использования Arc

Что сработало:

- **Записи как состояние.** `io.insert/update/find` хватило на полноценную
  машину состояний: шаг — строка, запуск — строка, переход — `update`.
  Перезапуск сервиса ничего не теряет.
- **`unique` вместо CAS.** `unique Claim.slot` даёт ровно ту атомарность,
  которая нужна лизу: вставка `runId:generation` — это и есть захват. Два
  параллельных тика в smoke дают `claimed = 1` на двоих.
- **Типы — это валидация входа.** `list<Step>` с обязательными полями отсекает
  мусор до тела: `delayMs: "soon"` не доходит до кода.
- **JSON в строке работает.** Граф шагов хранится как `steps: string`; это
  обходит вопрос «вложенный список записей в записи» и не мешает отдавать
  типизированный `WorkflowView`.

Что мешало:

- **`find` не умеет диапазоны.** «Все запуски с `nextAt <= now`» — главный
  запрос тика, а `where` сравнивает только на равенство. Пришлось делать два
  запроса по статусу и фильтровать в JS; `limit` применяется до фильтра, так
  что после 200 должных запусков часть молча не обрабатывается.
  [issue #20](https://github.com/chubakur/arcod/issues/20).
- **Имя сущности не проверяется.** `type WorkflowRec`, а в теле случайно
  `'Workflow'` — `check` молчит, запрос отдаёт `500 Internal` без имени
  сущности и без стектрейса в логах. Отладка — перезапуск и догадки.
  [issue #21](https://github.com/chubakur/arcod/issues/21).
- **Запись обязана иметь `id`, даже если ключ натуральный.** `Claim` с
  `slot` и `unique Claim.slot` выглядит легально, но вставка без `id` — 400
  `Invalid` без указания поля. Пришлось добавить `id = slot`.
  [issue #19](https://github.com/chubakur/arcod/issues/19).
- **Часов и таймеров нет.** `nextAt` — наша колонка, тик — внешний вызов.
  Язык не умеет «через 300 мс»; `cron` в `workflow` — минутный и статический.
  [issue #12](https://github.com/chubakur/arcod/issues/12).
- **CAS на обновлении нет.** `update` — last-write-wins. Захват построен на
  вставке уникального слота; для «изменить, если не изменилось» пришлось бы
  изобретать ещё одну таблицу. [issue #10](https://github.com/chubakur/arcod/issues/10).
- **Агрегатов нет.** `health` считает запуски страницами по 200. Для счётчика
  «сколько failed» это полный скан. [issue #15](https://github.com/chubakur/arcod/issues/15).

Чего не хватило для полной версии:

- версионирование определений (сейчас имя неизменяемо: `Conflict`);
- условные переходы и `join` (сейчас одна зависимость `after`, не список);
- вызов внешнего эффекта из шага (`remote`, `llm`, `queue.publish`) — действие
  пришлось ограничить локальными примитивами;
- лиз с TTL: claim вечен, поэтому упавший посреди волны тик оставляет
  поколение занятым. Повторный тик возьмёт следующее поколение, но шаг,
  записанный как `waiting` без `dueAt`, сам не оживёт.
