# 049-content-moderation — модерация контента с версиями политик

Система приёма и модерации пользовательского контента: автор отправляет текст,
фон проверяет его по активной версии политики, чистый контент одобряется
автоматически, рискованный попадает в очередь живого ревьюера. Решения можно
оспорить, апелляцию разбирает senior-ревьюер, а смена политики переоценивает
то, что старая политика одобрила автоматически.

Это не «сервис + kv»: здесь **четыре внешние системы** (Keycloak, Postgres,
Redis, MinIO), **пять провайдеров** и **три фоновых консьюмера**.

## Схема

```
                       ┌────────────────────┐
   автор/ревьюер ─────►│ Moderation (http)  │──── SQL ─────► Postgres
   Bearer JWT          │ auth op            │──── blob ────► MinIO
                       │                    │──── queue ───► Redis
                       └─────────┬──────────┘                  │
                                 │ JWKS                        ├─ screen   (оценка + S3)
                          ┌──────▼──────┐                      ├─ notify   (fan-out)
                          │  Keycloak   │                      └─ rescreen (новая политика)
                          └─────────────┘
```

Поток:

1. `POST /v1/items` пишет строку в статусе `screening` и публикует `screen`.
2. **screen** читает активную политику, считает риск (совпадения терминов × 30,
   каждая ссылка × linkWeight), кладёт снимок проверки в S3 и либо одобряет
   автоматически (`decidedBy: policy:vN`), либо ставит в очередь с дедлайном 24 ч.
3. **notify** раскладывает уведомления автору и ревьюерам; id уведомления
   детерминированный, повторная доставка не создаёт дубль.
4. Ревьюер выносит решение; повторное решение по той же строке — `409`.
5. Автор подаёт одну апелляцию; senior выносит `uphold`/`overturn`, что меняет
   статус контента.
6. Новая политика деактивирует старую и публикует `rescreen`: **rescreen**
   переоценивает всё, что было одобрено `policy:*`, и возвращает в очередь то,
   что теперь выше порога. Решения людей не перезаписываются.
7. `POST /v1/sweep` (внешний runner, своего cron в Arcod нет — #12) эскалирует
   просроченную очередь и апелляции; флаг липкий, повторный sweep идемпотентен.

## Компонент → provider

| Компонент | Provider | Что делает |
|-----------|----------|------------|
| Вход и токены | `identity` → keycloak | JWT по JWKS, `io.actor()` даёт id/name |
| Политики, контент, решения, апелляции, аудит | `sql` → postgres | Reviewer, Policy, Item, Decision, Appeal, Notification, Audit |
| Снимки проверки | `blob` → minio (s3) | `evidence/<itemId>.json` |
| Очередь и dead-letter | `queue` → redis | screen / notify / rescreen |
| Идентификаторы | `ids` → local | uuid строк и объектов |

Внешние системы в `docker-compose`: **postgres**, **redis**, **minio**,
**keycloak** (все четыре поднимает `arcod run --impl`).

## API

Все операции, кроме `sweep` и `dead`, — `auth op`: без Bearer-токена они
отвечают `401`. Роли хранятся в таблице Reviewer, а не в токене.

| Метод и путь | Кто | Назначение |
|--------------|-----|------------|
| `POST /v1/reviewers` | any auth | первый становится admin, остальные — reviewer |
| `POST /v1/reviewers/:id/role` | admin | выдать reviewer/senior/admin |
| `POST /v1/policies` | admin | новая версия политики + событие rescreen |
| `GET /v1/policies` | any auth | история версий, новые сверху |
| `POST /v1/items` | any auth | отправить контент (post/comment/profile) |
| `GET /v1/items` | any auth | мои отправки |
| `GET /v1/items/:id` | автор или staff | запись + решения + апелляции |
| `GET /v1/items/:id/decision` | автор или staff | последнее человеческое решение |
| `GET /v1/items/:id/evidence` | staff | снимок проверки из S3 |
| `GET /v1/queue?status=pending` | staff | очередь ревью |
| `POST /v1/items/:id/decision` | staff | approve/reject, reject требует причину |
| `POST /v1/items/:id/appeal` | автор | одна апелляция на отклонённый item |
| `GET /v1/appeals?status=open` | staff | апелляции |
| `POST /v1/appeals/:id/resolve` | senior/admin | uphold или overturn |
| `GET /v1/notifications` | any auth | мой inbox (`?unread=true`) |
| `POST /v1/notifications/:id/read` | владелец | отметить прочитанным |
| `GET /v1/stats` | staff | счётчики, auto-approved, эскалации |
| `GET /v1/audit` | staff | аудит действий |
| `POST /v1/sweep` | public | эскалация по явному `now` |
| `GET /v1/dead` | public | dead-letter трёх консьюмеров |

### Консьюмеры

1. **screen** — оценка риска, снимок в S3, авто-одобрение или очередь.
2. **notify** — уведомления автору/ревьюерам, идемпотентно по id.
3. **rescreen** — переоценка авто-одобренного контента после новой политики.

## Запуск

```sh
cd 049-content-moderation
arcod check
arcod build --impl --port 8096
arcod run --impl --port 8096
./smoke.sh                 # build + run + HTTP-проверки, в конце PASS
arcod run --down --impl    # остановить
```

`smoke.sh` сам поднимает compose, получает токены Keycloak изнутри сети и
проверяет: анонимный 401, бутстрап админа, запрет самоповышения, версии
политик, авто-одобрение, риск 70 и очередь, 403 автору, 409 на второе решение
и вторую апелляцию, 403 reviewer на resolve, overturn, rescreen после политики
v2, счётчики, идемпотентный sweep, owner-only уведомления, аудит и пустой
dead-letter.

## Опыт использования Arc

Что сработало без обходов:

- Пять провайдеров в одном сервисе: `sql`, `queue`, `blob`, `identity`, `ids`.
- `auth op` + Keycloak: `io.actor()` стабилен, роли удобно держать в своей
  таблице; `io.users()` не понадобился.
- Три консьюмера с цепочкой `screen → notify`; `retry` и dead-letter работают.
- `unique Policy.version`, `unique Appeal.itemId`, `unique Decision.itemId` —
  бизнес-инварианты выражены декларативно, а не проверками в каждом теле.
- `io.find` с `where`, `order`, `limit` и `io.count` закрывают очередь,
  статистику и аудит без полного скана в теле.
- `io.blobPut/blobGet` со строкой JSON достаточно для снимка проверки.

Чего не хватило (все — уже открытые issue, новых багов в этом примере нет):

- **#12** — у job нет cron/периодического триггера. Sweep эскалации приходится
  вызывать снаружи; `dueAt` проверяется только по запросу.
- **#58** — у `io.update` нет предусловия/CAS. Гонку двух ревьюеров закрывает
  `unique Decision.itemId`: второй insert получает 409 и до update не доходит.
  Без уникального правила оба прошли бы проверку статуса.
- **#64** — `auth op` без объявленного `error Unauthorized` отдаёт 500 вместо
  401. Здесь `Unauthorized` объявлен во всех auth-операциях заранее, поэтому
  анонимный запрос корректно даёт 401.
- **#60** — нет исходящего HTTP и почты: ревьюерам уходят только внутренние
  уведомления, письма/Slack/webhook из job не отправить.
- **#48** — `io.blobPut` принимает только строку: снимок проверки — JSON-текст,
  бинарные вложения (например, скриншот) пришлось бы кодировать base64.
- **#63** — TTL-кэш рядом с `sql`-сервисом недоступен (A094); дедуп и очередь
  живут в Postgres, отдельный kv не подключён.
- **#26** — olap/clickhouse по-прежнему только инфраструктура: аналитику по
  решениям считаем `io.count`/`io.find`, а не в OLAP.

Ограничения реализации: скоринг — намеренно простой (словарь терминов + ссылки),
без ML-модели; «senior» — роль в таблице, а не realm-роль Keycloak.

Проверки: `arcod check` — 0 ошибок, 20 W012 (у операций нет примеров в
контракте); `./smoke.sh` → **PASS**.
