# 016 — Аукцион: ставки, антиснайпинг, закрытие лота, письма

Система маленького аукциона: лот живёт до назначенного момента, ставки
принимаются по правилам (минимальный шаг, «нельзя перебить себя»,
антиснайпинг), закрывающий тик превращает время в вердикт, а консьюмер
рассылает письма продавцу и победителю через внешний почтовый шлюз.

## Компоненты

```
           POST /v1/lots            POST /v1/lots/:id/bids
клиент ────────────────►  Auction  ◄────────────────────── клиент
                            │  │
              store (sql)   │  │  events (queue)
                            ▼  ▼
                        MySQL   Redis ──► job notify ──► Mailer (HTTP) ──► SMTP/ESP
                            ▲                                  ▲
       POST /v1/admin/close │                                  │
   (workflow cron в prod)   └── Lot / Bid / Notification ──────┘
```

- **Auction** — единственный HTTP-сервис: CRUD лота, приём ставки, тик
  закрытия, статистика.
- **MySQL** — лоты, ставки, квитанции писем; деньги целыми центами, время
  эпохой в секундах.
- **Redis (queue)** — outbox-сообщение `notify` на каждый закрытый лот;
  at-least-once, ретраи 2, dead letter.
- **Mailer** — внешний почтовый шлюз (`external service Mailer : http`).
  В примере это мок `mock/mailer.mjs`, повторяющий API вендора
  (`POST /api/v1/send`), в жизни — ESP/SMTP-прокси.
- **job notify** — фоновый консьюмер: идемпотентен по строке `Notification`,
  поэтому повторная доставка не дублирует письмо.

### Компонент → provider

| Компонент | Capability | Provider | Где |
|-----------|------------|----------|-----|
| Лоты, ставки, квитанции | `sql` | mysql 8.4 | `bind store -> mysql` |
| Очередь закрытий | `queue` | redis 7 | `bind events -> redis` |
| Идентификаторы | `ids` | local | `bind uuid -> local` |
| Почтовый шлюз | внешний сервис | endpoint | `bind Mailer -> endpoint` |

Внешние системы в docker-compose: **MySQL** и **Redis**; третья — почтовый
шлюз, поднятый рядом (мок на той же compose-сети под именем `mailer`).

## API

| Метод | Путь | Что делает |
|-------|------|------------|
| POST | `/v1/lots` | создать лот: старт, резерв, длительность |
| POST | `/v1/lots/:lotId/bids` | ставка: шаг +100, нельзя перебить себя, антиснайпинг |
| GET | `/v1/lots/:lotId` | лот и история ставок (свежие сверху) |
| POST | `/v1/admin/close` | закрыть все просроченные лоты, поставить `notify` |
| GET | `/v1/stats` | закрытые лоты, оборот ставок (агрегат), письма |
| POST | `/v1/dev/seed` | два демо-лота |
| POST | `/v1/dev/lots/:lotId/expire` | dev-помощник: сдвинуть конец в прошлое |

Правила ставки:

1. Первая ставка — не ниже `startCents`, дальше — не ниже текущей + 100.
2. Тот же участник не может перебить сам себя (409).
3. Ставка в последние 60 секунд двигает конец на +120 секунд, не более
   трёх раз; `extensions` виден в лоте.
4. Закрытие: `highBid >= reserveCents` → `sold`, иначе `unsold`;
   проигравшие ставки помечаются `lost`.

## Запуск

```bash
arcod check
arcod build --impl --port 8093
arcod run --impl --port 8093      # mysql + redis + сервис
./smoke.sh                        # полный сценарий, в конце PASS
arcod run --down --impl           # или docker compose down -v
```

`smoke.sh` сам собирает образ, поднимает мок почтового шлюза в compose-сети
под именем `mailer` и проверяет: ставки и три отказа, антиснайпинг +120 с,
закрытие sold/unsold, три письма (продавец дважды, победитель один раз),
агрегат оборота, идемпотентность второго тика и 404.

## Опыт использования Arc

Что легло хорошо:

- `store.aggregate(... op: 'sum')` — единственный вызов вместо вычитки всех
  ставок; деньги в центах складываются на стороне MySQL (#34 проверен здесь).
- Очередь + `job` + `retry`: outbox в SQL и консьюмер работают без
  ручной склейки; dead letter видно в Redis.
- `external service` + `io.remote` — вендор описан контрактом, мок подменяет
  его без правок тела.
- Один и тот же код прошёл `check` → `build --impl` → `run --impl` без
  правок спеки.

Чего не хватило (issue в `chubakur/arcod`):

- **Расписание.** Закрывающий тик — это `POST /v1/admin/close`; cron-триггер
  есть только у `workflow`, и вызвать операцию по времени из модели нельзя.
  В README честно: в продакшене тик дёргает внешний планировщик (#40).
- **Два сервиса в одном модуле.** Спека с `service Store` и `service Cache`
  проходит `check` без ошибок, но в compose попадает только первый, а
  маршруты второго отвечают 404 — молчаливая потеря (#41).
- **Внешний endpoint на Docker Desktop.** `localhost` в `endpoint`/URL
  переписывается в `host.docker.internal`, у которого в контейнере есть
  AAAA-адрес; `fetch` выбирает IPv6 и падает, хотя IPv4 отвечает. Пришлось
  ставить мок в compose-сеть под именем `mailer` (#42).
- Мелочи: в `impl` нет общего модуля (повторяющиеся хелперы с уникальными
  именами — #39, закрыт диагностикой A093); тела не видят `now()` — время
  берётся из `Date`, и скачок часов хоста делает «просроченные» лоты
  будущими. Поэтому в smoke есть dev-операция `expire`.

## Файлы

- `main.arc` — модель: типы, контракт, job, environment.
- `impl/` — тела операций и консьюмера (по файлу на операцию).
- `mock/mailer.mjs` — почтовый шлюз: `POST /api/v1/send`, `GET /api/v1/messages`.
- `smoke.sh` — сборка, запуск, HTTP-проверки, PASS.
