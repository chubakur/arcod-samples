# 006 — Mini search

Небольшой поисковый движок: документы, инвертированный индекс, ранжирование
BM25 и подсветка совпадений в сниппете. Всё состояние — записи в kv-хранилище,
все запросы — HTTP. Это backend-пример: модель, API, Redis и e2e-проверка; UI
нет.

## Зачем

Полнотекстовый поиск — хороший тест для языка, потому что в нём сходятся
несколько неудобных требований сразу:

* запись документа — это не одна запись, а десятки связанных строк;
* переиндексация должна быть видимой атомарно: клиент не должен увидеть
  половину старого и половину нового документа;
* два одновременных писателя не должны склеить две разные версии индекса;
* запрос должен читать индекс, а не сканировать все документы;
* ранг — это число, а не порядок вставки.

Arcod не даёт транзакций на несколько записей и не даёт compare-and-swap
(chubakur/arcod#10). Пример показывает, как из этого собрать корректную
переиндексацию: **версии и уникальные составные ключи**.

## Модель

```arcod
type Doc = {
  id: uuid, title: string, body: string, tags: string,
  length: int, version: int, createdAt: datetime, updatedAt: datetime
}

type Posting = {
  id: string, term: string, docId: uuid,
  version: int, tf: int, titleTf: int
}

type Term = { id: string, term: string, at: datetime }
type Corpus = { id: string, documents: int, totalLength: int, updatedAt: datetime }
```

`Doc` — точка фиксации. Постинги версии `N` невидимы, пока `Doc.version`
не станет `N`. Поэтому замена документа выглядит так:

1. записать постинги новой версии (`version + 1`);
2. обновить `Doc` — это и есть коммит;
3. убрать постинги старых версий best-effort.

Если писатель упал между шагами 1 и 2, новые постинги просто не участвуют в
поиске. Если два писателя выбрали одну версию, составной ключ
`unique Posting.(term, docId, version)` пропускает только одного; проигравший
получает `Conflict` и убирает свои частичные постинги.

`Corpus` — денормализованные счётчики для BM25. Их можно потерять при гонке
(снова #10), поэтому `/v1/stats` возвращает и `documents` из `Corpus`, и
`scannedDocs` — то, что реально доказано обходом записей.

## API

| Метод | Путь | Что делает |
|-------|------|------------|
| POST | `/v1/docs` | индексирует документ: `{title, body, tags?}` |
| PUT | `/v1/docs/:id` | заменяет документ и переиндексирует его |
| GET | `/v1/docs/:id` | читает документ; нет — 404 |
| DELETE | `/v1/docs/:id` | удаляет документ и его постинги |
| GET | `/v1/search?q=...&limit=10&offset=0` | ранжированный поиск |
| GET | `/v1/suggest?prefix=...&limit=8` | подсказки по словарю терминов |
| GET | `/v1/stats` | счётчики индекса |
| GET | `/v1/health` | живость и число документов |

`POST /v1/docs` возвращает `{doc, postings, terms}`;
`PUT` — то же плюс новый `doc.version`; `DELETE` — `{deleted, postings}`.

## Язык запросов

| Синтаксис | Смысл |
|-----------|-------|
| `word` | необязательный терм, участвует в ранге |
| `+word` | обязательный терм |
| `-word` | документ с этим термом исключается |
| `"exact phrase"` | фраза проверяется по тексту документа |
| `tag:name` | фильтр по тегу (можно несколько) |

По умолчанию условия объединяются через **OR**; обязательные термы, минус-
термы, фразы и теги — это фильтры, они должны выполняться все. Поэтому
`tag:search` без содержательного терма — это 400: тег не порождает кандидатов
из индекса. Правильный запрос: `ranking tag:search`.

Ранжирование — BM25 (`k1 = 1.2`, `b = 0.75`) с бустом `×1.6`, если терм
встретился в заголовке. `df` считается по живым постингам кандидатов, `N` и
средняя длина — по `Corpus`. Сниппет — 200 символов вокруг первого совпадения,
совпадения обёрнуты в `<mark>...</mark>` (HTML уже экранирован).

## Запуск

```bash
arcod check
arcod build --impl
arcod run --impl --port 8093
./smoke.sh                 # build + run + HTTP-проверки, в конце PASS
arcod run --down --impl
```

Если `arcod` не в PATH, тот же сценарий принимает путь:

```bash
ARCOD=/path/to/arcod/bin/arcod.mjs PORT=8093 ./smoke.sh
```

Пример использования:

```bash
curl -s -X POST localhost:8093/v1/docs -H 'content-type: application/json' \
  -d '{"title":"Inverted index basics","body":"An inverted index maps terms to documents.","tags":"search"}'

curl -s 'localhost:8093/v1/search?q=%22inverted%20index%22' | jq
curl -s 'localhost:8093/v1/search?q=ranking%20tag:search' | jq
curl -s 'localhost:8093/v1/suggest?prefix=inv' | jq
```

## Опыт использования Arc

**Что сработало хорошо.**

* Составной `unique Posting.(term, docId, version)` — это ровно тот
  примитив, которого не хватало для индекса. Без него пришлось бы склеивать
  `term#docId#version` в одно поле и объяснять это в модели. Составной ключ
  проверен на чистом состоянии (19.11.2026, `c72e338`): две одинаковые пары
  дают 409, разные версии одной пары — нет (chubakur/arcod#13, закрыт).
* Версия как точка фиксации отлично ложится на «запись — набор записей»:
  постинги можно писать в любом порядке, видимость переключает один
  `io.update` документа.
* `io.find` с `in`, `gte`/`lt` и курсором покрывает и выборку по терминам, и
  префиксные подсказки, и пакетную загрузку документов-кандидатов
  (`where: {id: {in: chunk}}`) без N+1. Один и тот же код работает на kv и sql.
* `arcod test --impl` прогоняет примеры из `main.arc` против настоящих тел:
  4/4 проходят, включая переиндексацию и удаление.

**Чего не хватило.**

* **Нет транзакции на несколько записей.** Пришлось строить версионный
  протокол и руками убирать частичные постинги. Это работает, но каждый
  писатель обязан знать про порядок шагов. Транзакция или batch-запись с
  одним commit-маркером сделала бы модель проще.
* **Нет CAS/атомарного счётчика** (chubakur/arcod#10). `Corpus` может
  разъехаться с фактическим числом документов; поэтому в `/v1/stats` есть
  `scannedDocs` и видно расхождение.
* **Нет `count`/агрегатов.** Чтобы посчитать постинги и термины, `/v1/stats`
  листает все страницы по 500 записей. Для честного счётчика нужен `io.count`
  или агрегат в адаптере (chubakur/arcod#15).
* **Один файл на операцию и нет общих модулей** (chubakur/arcod#11). Токенайзер
  и стоп-лист продублированы в `indexDoc`, `updateDoc`, `search` и `suggest` с
  разными префиксами. Теперь сборка хотя бы отказывает при совпадении имён
  (проверено: `arcod build --impl` → `duplicate top-level name "LINES"`), но
  вынести общий код по-прежнему некуда.
* **В примерах нельзя прочитать элемент списка.** `hits[0].title` парсится как
  вызов с member-callee и падает с `unsupported call expression`; приходится
  проверять только `page.total` и `page.hits != null`, хотя именно ранг —
  главное, что хочется закрепить примером (chubakur/arcod#16).
* **Нет стемминга и позиций термов.** Это ограничение примера, не языка:
  индекс хранит точные словоформы, фраза проверяется как подстрока. Для
  русской морфологии понадобился бы внешний стеммер, а для фраз — позиции в
  постинге.

**Ограничения примера.** Запрос читает не больше 5000 постингов; тег без
содержательного терма не поддерживается; `Corpus` может отставать от факта;
удаление чистит постинги best-effort (на ответы это не влияет — поиск всё
равно отбрасывает постинги без `Doc`).
