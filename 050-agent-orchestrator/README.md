# 050-agent-orchestrator: LLM-агент с инструментами, шагами и бюджетом

Платформа, которая запускает LLM-агента на задачу: агент — это промпт и
**закрытый список инструментов**, прогон — это очередь, шаги, след в S3 и счёт
за токены. Модель не получает прямой доступ к сети: каждый вызов инструмента
проходит через песочницу, и инструмент вне allow-list валит прогон, а не
уходит наружу.

Это не «сервис + kv»: здесь пять внешних систем, фоновая петля на два
консьюмера и внешний HTTP-инструментарий.

## Компоненты

```
   client
     │  POST /v1/agents/:id/runs
     ▼
┌──────────────────────────┐      publish execute      ┌──────────────────┐
│ Orchestrator (Node)      │ ────────────────────────► │ redis (queue)    │
│  API: agents, runs,      │                           │ execute, finished│
│  cancel, stats, sweep    │ ◄──────────────────────── │                  │
└──────┬─────────┬─────────┘        consume            └──────────────────┘
       │         │
       │         │ JSON trace                ┌──────────────────────────┐
       │         └─────────────────────────► │ minio (S3)               │
       │            runs/<id>.json           │ billing/<id>.json        │
       │                                     └──────────────────────────┘
       │ SQL
       ▼
┌──────────────┐        ┌────────────────────────┐      ┌──────────────────┐
│ postgres     │        │ execute (consumer)     │─────►│ llm endpoint     │
│ Agent        │◄───────│ шаг: chat → tool → шаг │      │ OpenAI-compatible│
│ Run, Step    │        └───────────┬────────────┘      └──────────────────┘
│ Usage        │                    │ io.remote
└──────────────┘                    ▼
                          ┌────────────────────────┐
                          │ tools sandbox (HTTP)   │
                          │ lookup/refund/sleep    │
                          └────────────────────────┘
```

### Компонент → provider

| Компонент | provider | Что делает |
|-----------|----------|------------|
| Состояние (Agent, Run, Step, Usage) | `sql` → `postgres` | строки, `unique`-ключи, счётчики и суммы |
| Очередь (`execute`, `finished`) | `queue` → `redis` | доставка между API и консьюмерами |
| Следы и чеки | `blob` → `s3` (minio) | `runs/<id>.json`, `billing/<id>.json` |
| Модель | `llm` → `openai(baseUrl: …)` | `io.chat`: любой OpenAI-совместимый endpoint |
| Инструменты | `endpoint` → внешний HTTP | `POST /v1/tools/call`, вызов через `io.remote` |
| Идентификаторы | `ids` → `local` | id прогонов, шагов, usage |

Пять внешних систем: postgres, redis, minio, модель, песочница инструментов.
Модель и инструменты в примере — `mocks/upstream.mjs` на хосте (порты 9099 и
9098); в проде это Ollama/облачный роутер и внутренний API.

## Модель данных

* **Agent** — имя (уникальное), системный промпт, `tools` (через запятую),
  `maxSteps`, `tokenBudget`, цены `pricePer1kTokens`/`pricePerToolCall`.
* **Run** — вход, `clientRef` (уникальный ключ идемпотентности), статус,
  счётчики шагов/токенов/вызовов, ответ, ошибка, флаг отмены, ключ следа.
  Статусы: `queued | running | succeeded | failed | budget_exceeded | cancelled`.
* **Step** — один ход: `kind: tool | final | denied | error`, имя инструмента,
  аргументы и результат (JSON-строки), токены. Это durable-транскрипт: после
  переотправки сообщения петля восстанавливает диалог из шагов и продолжает,
  а не начинает заново.
* **Usage** — одна строка на прогон: токены, вызовы, сумма, ключ чека.
  `unique Usage.runId` — вторая защита от двойного счёта.

## API

| Метод | Путь | Что |
|-------|------|-----|
| POST | `/v1/agents` | создать агента; дубль имени — 409, пустой промпт — 400 |
| GET | `/v1/agents` | список агентов |
| POST | `/v1/agents/:agentId/runs` | поставить прогон в очередь; тот же `clientRef` вернёт тот же прогон |
| GET | `/v1/runs?status=&limit=` | журнал прогонов |
| GET | `/v1/runs/:runId` | прогон и его шаги |
| GET | `/v1/runs/:runId/trace` | JSON-след из S3 (`key`, `content`, `bytes`) |
| POST | `/v1/runs/:runId/cancel` | 200; queued отменяется сразу, running получает флаг |
| POST | `/v1/sweep` | пометить зависшие `running` как `failed` (вместо cron, #12) |
| GET | `/v1/stats` | прогоны по статусам, токены, вызовы, начислено |
| GET | `/v1/dead` | dead-letter очереди `execute` |

## Петля агента

1. `startRun` вставляет `Run(queued)` и публикует `execute`.
2. Консьюмер `execute` переводит прогон в `running` и на каждом шаге:
   * проверяет `cancelRequested`;
   * зовёт `io.chat(messages, system)`, где system требует один JSON-объект;
   * `{"tool":"…","args":{…}}` → проверка allow-list → `io.remote('Tools','call')`
     → шаг `tool` → наблюдение возвращается в диалог;
   * `{"final":"…"}` → шаг `final`, прогон `succeeded`;
   * после каждого шага: `tokens >= tokenBudget` → `budget_exceeded`;
     `seq >= maxSteps` без ответа → `failed`.
3. Финал: след в S3, обновление `Run`, публикация `finished`.
4. Консьюмер `invoice` считает сумму (`ceil(tokens/1000)*price + calls*price`),
   пишет чек в S3 и строку `Usage`; повторная доставка находит строку и
   ничего не добавляет.

Токены считаются оценкой `ceil(chars/4)`: `io.chat` не возвращает `usage`
(issue #65), а настоящий счётчик нужен бюджету уже сегодня. Это названо в
README честно, а не спрятано.

## Запуск

```bash
cd 050-agent-orchestrator
./smoke.sh                     # mock-модель + mock-инструменты, сборка, прогон, проверки
```

Вручную:

```bash
node mocks/upstream.mjs &      # :9099 модель, :9098 инструменты
arcod check
arcod build --impl --port 8097
arcod run --impl --port 8097
# в другом терминале:
curl -s -X POST localhost:8097/v1/agents -H 'content-type: application/json' \
  -d '{"name":"support","systemPrompt":"You answer questions about orders.","tools":"lookup_order,refund_order,sleep","tokenBudget":4000}'
curl -s -X POST localhost:8097/v1/agents/<id>/runs -H 'content-type: application/json' \
  -d '{"input":"Where is order 1042?","clientRef":"c-1"}'
arcod run --down --impl
```

На Linux контейнер не видит loopback хоста: `host.docker.internal` нужно
добавить в `extra_hosts` (Docker Desktop на macOS делает это сам).

## Опыт использования Arc

**Что получилось хорошо.**

* `unique` на `Run.clientRef` и `Usage.runId` — ровно те гарантии, которые
  нужны очереди и биллингу: без них повторная доставка удваивала бы прогоны и
  счета.
* `queue` + `job` с одним параметром работает как надо: payload — строка id,
  консьюмер получает её значением.
* `io.aggregate` (sum по `tokens`, `toolCalls`, `amount`) и `io.count` по
  статусам дают `/v1/stats` без полного скана; #34 действительно закрыт.
* Долговечные шаги в SQL + идемпотентность по ключу дают восстановление после
  переотправки: петля продолжает с того же места. Это не «фича Arcod», но
  язык не мешает её построить.
* `status: 200` на `cancelRun` (#47) убирает самый раздражающий 201 у
  идемпотентного действия.

**Чего не хватило — с issue.**

* **#65 — `io.chat` не отдаёт `usage`.** Сигнатура
  `chat(messages, system) -> {content, model}`. Провайдер присылает
  `usage.prompt_tokens/completion_tokens`, клиент их выбрасывает, и бюджет
  агента считается по длине строк. Для платформы, которая берёт деньги за
  токены, это не косметика.
* **#66 — у `llm.chat` нет `tools`/`tool_calls`.** Модель вынуждена отвечать
  JSON-текстом, а рантайм — парсить его и надеяться, что формат не поехал.
  OpenAI-совместимые endpoint'ы умеют `tools` и структурированный
  `tool_calls`; язык это не выражает.
* **#67 — `openai(baseUrl:)` не переписывает `localhost`.** `endpoint` после
  #42 заменяет loopback на `host.docker.internal`, а llm-биндинг — нет:
  одинаковый по смыслу адрес ведёт себя по-разному. Пришлось писать
  `host.docker.internal` прямо в спеке (и это ломается на Linux без
  `extra_hosts`).
* **#46 (open)** — отмена кооперативная: шаг с `io.remote`/моделью
  дорабатывает. Петля проверяет флаг между шагами и честно пишет
  `cancelled`; «прервать звонок» нельзя.
* **#12 (open)** — cron у job нет, поэтому `sweep` зависших прогонов —
  публичный `POST /v1/sweep` с явным `now`; снаружи его должен дёргать runner.
* **#56 (open)** — повторный `POST` с тем же `clientRef` возвращает исходный
  прогон, но отвечает 201 (объявленный статус), а не 200. Клиент вынужден
  смотреть на id, а не на код.

**Обходы, которые стоит знать.**

* Пустой `clientRef` при `unique`-правиле нельзя хранить как `""`: второй
  прогон упал бы на уникальности. Сервер выдаёт uuid и возвращает его в
  `clientRef` — идемпотентность остаётся, а пустых ключей нет.
* Инструмент вне allow-list проверяется **до** `io.remote`: иначе «модель
  придумала инструмент» превращалось бы в сетевой вызов.
* `io.remote` отдаёт `{status, body}` (#32); тело инструмента — `body.output`,
  а не `body.result`.

## Ограничения

* Токены — оценка, а не биллинг провайдера (#65).
* Инструменты описаны промптом, а не JSON-схемой (#66).
* Отмена не прерывает текущий шаг (#46).
* Sweep — внешний вызов, а не расписание (#12).
* Следы пишутся в конце прогона: упавший посреди шага прогон имеет шаги в SQL,
  но trace появляется только после `sweep`/финала.
