# 043-event-log

Журнал событий заказов: append-only лог в Postgres, проекция для чтения,
переигрывание (replay) как штатная операция и упаковка сегментов лога в S3.
Клиент пишет события с ожидаемой версией агрегата, читает состояние из
проекции, а при смене логики проекции может пересобрать её из лога.

Это система из трёх внешних хранилищ и трёх фоновых консьюмеров, а не
«сервис + kv»:

- **Postgres** — потоки, события (журнал), проекция заказов, чекпоинты, аудит
  архивов;
- **Redis** — очередь заданий (project / rebuild / archive) и outbox-relay;
- **MinIO (S3)** — JSONL-сегменты лога, по одному объекту на упакованную
  версию потока;
- **три консьюмера** — построение проекции, пересборка проекции, упаковка в S3;
  HTTP-ответ не ждёт ни одного из них.

## Схема компонентов

```
  POST /v1/streams/:id/events
        │ expectedVersion = version
        ▼
  ┌─────────────┐   insert event(streamId, seq)      ┌──────────────┐
  │  Ledger     │───────────────────────────────────►│  Postgres    │
  │  (http)     │   update stream.version            │  Stream      │
  │             │   outbox: events.project           │  Event       │
  └──────┬──────┘                                    │  OrderView   │
         │ publish (outbox, same tx)                 │  Checkpoint  │
         ▼                                           │  Archive     │
  ┌─────────────┐                                    └──────▲───────┘
  │   Redis     │                                           │ upsert
  │  queue      │──► job project(eventId) ──────────────────┘
  │             │──► job rebuild(streamId) ──► удалить view, свернуть лог
  │             │──► job pack(streamId) ─────► io.blobPut ──► MinIO (S3)
  └─────────────┘                                   │
                                                    ▼
                                     GET /v1/streams/:id/archive
                                     (JSONL обратно из S3)
```

## Компонент → provider

| Компонент | Provider | Где |
|-----------|----------|-----|
| Потоки, журнал, проекция, чекпоинты, архивные записи | `sql` (алиас `store`) | Postgres `db:5432` |
| Очередь project / rebuild / archive | `queue` (алиас `events`) | Redis `queue:6379` |
| Сегменты лога JSONL | `blob` (алиас `archive`) | MinIO `s3:9000`, ключи `streams/<name>/v<version>.jsonl` |
| Быстрый указатель «до какого seq дочитан поток» | `kv` (алиас `cursor`) | таблица `arcod_kv` в том же Postgres |
| Идентификаторы событий | `ids` (алиас `uuid`) | локально |

Внешние системы в `docker-compose` (генерируется `arcod build`): `db`
(Postgres), `queue` (Redis), `s3` (MinIO) — три контейнера плюс сервис.

## API

| Метод и путь | Что делает | Ошибки |
|--------------|------------|--------|
| `POST /v1/streams` | создать поток по имени; повтор возвращает существующий | 400 Invalid |
| `GET /v1/streams/:streamId` | текущая версия и число событий | 404 |
| `POST /v1/streams/:streamId/events` | append: `type`, `payload` (JSON-строка), `expectedVersion` | 400, 404, 409 |
| `GET /v1/streams/:streamId/events?limit=` | журнал по возрастанию `seq` | 400 |
| `GET /v1/orders/:streamId` | проекция заказа (status, total, lines, lastSeq) | 404 |
| `GET /v1/projections` | чекпоинты консьюмеров | — |
| `POST /v1/streams/:streamId/replay` | поставить пересборку проекции | 404 |
| `POST /v1/streams/:streamId/archive` | поставить упаковку лога в S3 | 404 |
| `GET /v1/streams/:streamId/archive` | последний сегмент из S3 целиком (key, events, bytes, content) | 404 |
| `GET /v1/stats` | потоки / события / проекции / архивы | — |

`expectedVersion` — это оптимистичная блокировка: append с устаревшей версией
получает 409 и ничего не пишет. `payload` хранится как пришёл (строка JSON),
поэтому журнал не зависит от схемы событий.

## Как это работает

**Append.** Сначала читается `Stream.version`, сравнивается с
`expectedVersion`, затем вставляется событие с `seq = version + 1`.
`unique Event.(streamId, seq)` — вторая линия обороны: если два клиента
прошли проверку одновременно, один INSERT упадёт и вернёт 409, история не
получит две записи с одним `seq`. Версия потока двигается после вставки: при
падении между шагами журнал полный, а указатель отстаёт на один — следующий
append это увидит как устаревшую версию, а не запишет дубль.

**Проекция.** `job project` читает одно событие, сверяет `OrderView.lastSeq`
и применяет `order.created/paid/shipped/cancelled`. Повторная доставка —
no-op. Чекпоинт пишется в SQL (его видно в `GET /v1/projections`) и в kv как
O(1)-указатель.

**Replay.** `job rebuild` удаляет проекцию потока и сворачивает журнал заново.
Это единственный путь починки после изменения тела проекции: лог — источник
истины, проекция расходна.

**Архив.** `job pack` собирает JSONL, кладёт объект в S3 и только потом
пишет строку `Archive`. Повтор пишет тот же ключ. `GET .../archive` читает
байты из S3, а не перерисовывает их из SQL, — так smoke проверяет реальный
объект.

## Запуск

```sh
arcod check
arcod build --impl --port 8095
arcod run --impl --port 8095
./smoke.sh            # PORT=8095 по умолчанию; ARCOD=... чтобы взять другой бинарь
arcod run --down --impl   # или docker compose -f .arcod/build/docker-compose.yml down -v
```

`smoke.sh` проверяет: идемпотентное создание потока, три append'а, 409 на
устаревшую версию, порядок журнала, догон проекции до `seq 3` (status/total/
lines), чекпоинт, пересборку из лога, конфликт + успешный retry, упаковку в S3
и чтение объекта обратно, счётчики, 400 на пустой тип и 404 на неизвестный
поток. В конце печатает `PASS`.

## Опыт использования Arc

Что сработало:

- `unique Event.(streamId, seq)` — составной уникальный индекс поддержан
  (парсер принимает `unique Entity.(a, b)`), duplicate key приходит как
  объявленный `Conflict`, а не как 500.
- `queuePublish` внутри операции действительно уезжает через outbox: событие
  и задание на проекцию не расходятся.
- Три консьюмера в одном сервисе с разными topic, `retry` и эффектами —
  `check` раскладывает эффекты по заданиям без ручной настройки.
- `io.blobPut/blobGet` с content-type `application/x-ndjson` и обратное
  чтение байтов работают; `TextEncoder` в теле задания доступен.

Чего не хватило и что обошли:

- **Конкурентный append с `events.publish` теряет записи** —
  [#57](https://github.com/chubakur/arcod/issues/57). Два параллельных POST с
  одним `expectedVersion`: один 409, второй 500
  (`postgres 25P02: current transaction is aborted`), и в базе не остаётся
  **ни одной** строки — откатывается и победитель. Без `events.publish` та же
  гонка даёт честные 201/409, то есть виноват транзакционный путь операции.
  Поэтому в `smoke.sh` гонка не проверяется: проверяется последовательный
  конфликт и retry. Для реального использования это блокер.
- **Нет примитива «прочитать версию и записать следующую атомарно»**. CAS
  приходится строить на `fetch` + `unique`, и от гонки защищает только
  индекс. При починке #57 было бы достаточно транзакции на запрос с
  изоляцией, но в спеке такого эффекта нет.
- **OLAP-капабилити нет.** Идея 030 предполагала ClickHouse для аналитики;
  `uses x: olap` теперь падает на `check` с `A076 capability olap has no
  effects and no adapter` (это закрытие
  [#26](https://github.com/chubakur/arcod/issues/26)), провайдер
  `clickhouse` остаётся мёртвым контейнером. Аналитика здесь читается из
  SQL-проекции; отдельного OLAP-слоя в примере нет.
- **kv внутри sql-сервиса живёт в `arcod_kv` того же Postgres**, и попытка
  привязать alias к redis — ошибка `check` с подсказкой. Это хорошо
  диагностируется, но «два kv в одном сервисе на разных бэкендах» так не
  сделать.
- `io.save` по-прежнему ждёт конверт `{ b, h }`, а не голый объект
  ([#52](https://github.com/chubakur/arcod/issues/52)); в заданиях это
  написано явно, иначе `load().b` пуст без единой ошибки.
