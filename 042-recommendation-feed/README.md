# 042-recommendation-feed

Рекомендательная лента для каталога товаров: события пользователей, модель
«товар ↔ товар» по совместным касаниям и лента, которая отдаёт соседей уже
просмотренного, а на холодном пользователе — взвешенную популярность.

Это система из трёх внешних хранилищ и двух фоновых консьюмеров, а не
«сервис + kv»:

- **Postgres** — каталог, события, признаки пар, аудит версий модели;
- **Redis** — очередь (recompute / snapshot) и outbox-relay;
- **MinIO (S3)** — версионированные снапшоты модели;
- **два консьюмера** — пересчёт признаков по пользователю и сборка снапшота.

## Схема компонентов

```
                 POST /v1/events                GET /v1/feed/:userId
                        │                               │
                        ▼                               ▼
              ┌───────────────────┐          ┌────────────────────┐
              │ Recommend (http)  │          │  kv: feed:pointer  │
              │  track / feed     │◄─────────┤  {version,key,...} │
              └───┬───────────┬───┘          └─────────▲──────────┘
                  │ insert    │ publish                │ save
                  ▼           ▼                        │
            ┌──────────┐  ┌──────────┐          ┌──────┴────────────┐
            │ Postgres │  │  Redis   │          │ job snapshot      │
            │ Item     │  │ recompute│─────────►│ (consumer 2)      │
            │ Interact.│  │ snapshot │          └───┬───────────┬───┘
            │ Touch    │  └────▲─────┘              │ put       │ insert
            │ ModelVer.│       │                    ▼           ▼
            └────▲─────┘  ┌────┴──────┐        ┌────────┐  ┌──────────┐
                 │        │ job       │        │  S3    │  │ ModelVer │
                 └────────┤ recompute │        │models/ │  │  (audit) │
                          │(consumer1)│        │ vN.json│  └──────────┘
                          └───────────┘        └────────┘
```

Читатель никогда не собирает модель сам: он берёт указатель из kv, читает
готовый снапшот из S3 и только фильтрует увиденное по своей истории.
Писатель — единственный консьюмер `snapshot`, который сначала кладёт объект,
потом двигает указатель, потом пишет аудит-строку.

## Компонент → provider

| Компонент | Provider | Где |
|-----------|----------|-----|
| Каталог, события, признаки пар, версии модели | `sql` → postgres | `db:5432` |
| Указатель на текущую модель | `kv` (алиас `pointer`) | таблица `arcod_kv` в том же postgres (см. ограничения) |
| Очередь recompute / snapshot | `queue` → redis | `redis:6379` |
| Снапшоты модели | `blob` → S3 | `s3:9000`, бакет `arcod` |
| Идентификаторы | `ids` → local | — |

Внешние системы в `docker-compose`: **postgres**, **redis**, **minio (S3)**.

## API

| Метод и путь | Что делает | Ошибки |
|--------------|------------|--------|
| `POST /v1/items` | добавить товар в каталог | 400 Invalid, 409 Conflict (дубль title) |
| `GET /v1/items` | каталог | — |
| `POST /v1/events` | принять касание: `clientEventId, userId, itemId, kind ∈ view/cart/buy` | 400 Invalid, 409 Conflict |
| `GET /v1/feed/:userId?limit=10` | лента: соседи просмотренного, затем популярность | 400 Invalid |
| `POST /v1/model/rebuild` | опубликовать задание сборки | — |
| `GET /v1/model` | текущая версия и её размеры | — |
| `GET /v1/model/snapshot` | тело снапшота из S3 (для отладки и smoke) | 404 NotFound |
| `GET /v1/stats` | товары / события / признаки / версия | — |

Пример:

```bash
curl -sX POST localhost:8094/v1/items -H 'content-type: application/json' \
  -d '{"title":"USB-C Hub","category":"dock","price":9000}'
curl -sX POST localhost:8094/v1/events -H 'content-type: application/json' \
  -d '{"clientEventId":"e-1","userId":"alice","itemId":"<id>","kind":"buy"}'
curl -s 'localhost:8094/v1/feed/dave?limit=5'
```

## Как считается модель

1. `track` пишет `Interaction` и в **той же транзакции** кладёт сообщение
   `recompute(userId)` в outbox: строка без задания невозможна.
2. Консьюмер `recompute` пересобирает признаки одного пользователя: для каждой
   пары его товаров пишет `Touch { id: "user|min|max", boost: min(весов) }`.
   Запись идемпотентна — повтор задания не раздувает счётчик.
3. Консьюмер `snapshot` суммирует `Touch` по парам, строит top-20 соседей на
   товар и top-50 популярности, кладёт JSON в S3, затем двигает указатель kv и
   пишет строку `ModelVersion`.
4. `feed` берёт снапшот, исключает всё, что пользователь уже трогал, и
   сортирует по сумме совместных касаний; пустые места добивает популярностью.

Веса: view=1, cart=2, buy=3. Признак пары — минимум весов двух касаний, то
есть «смотрел и купил» сильнее, чем «смотрел и смотрел».

## Запуск

```bash
arcod check
arcod build --impl
arcod run --impl --port 8094
./smoke.sh          # build + run + HTTP-проверки, печатает PASS
arcod run --down --impl
```

`smoke.sh` поднимает три контейнера, прогоняет каталог, идемпотентную
досылку события, оба консьюмера, чтение снапшота из S3, ленту по
co-occurrence, холодную популярность и лимиты.

## Опыт использования Arc

Что сработало без борьбы:

- `rules { unique ... }` на `Item.title`, `Interaction.clientEventId`,
  `Touch.id` — и в том числе настоящий 409 на гонке двух вставок (проверено
  после закрытия [#54](https://github.com/chubakur/arcod/issues/54)).
- Outbox: `io.queuePublish` внутри операции действительно атомарен с insert —
  строка и задание живут вместе.
- Два консьюмера в одном сервисе, у каждого свой topic и `retry: 2`.
- `io.blobPut/blobGet` с JSON-снапшотом на сотни килобайт, S3-бакет
  поднимается сам.
- `io.count` для статистики и `io.find` с `where` по строковому полю.

Чего не хватило (issue заведены/уже есть):

- **kv-указатель при `store: sql`** всегда живёт в таблице `arcod_kv`, а не в
  redis: `arcod check` отклоняет `bind pointer -> redis` (A094). Для этого
  примера приемлемо, но «горячий кэш указателя» так не построить —
  [#37](https://github.com/chubakur/arcod/issues/37).
- **`io.save` ждёт конверт `{ b, h }`**, а не голый объект: `save(key, {...})`
  молча пишет `{"h":null}`, и потом `load(key).b` пуст. Ошибки нет, лога нет;
  я поймал это только запросом в `arcod_kv` — #52.
- **Нет атомарного счётчика/CAS** для пары: пришлось хранить признаки
  по-пользовательски и суммировать при сборке, вместо `count += 1` —
  [#10](https://github.com/chubakur/arcod/issues/10).
- **Падение консьюмера не видно**: ошибка уходит в dead-letter очередь, в лог
  не печатается ничего. Именно поэтому первый прогон «модель не появилась»
  пришлось расследовать запросами в БД — [#55](https://github.com/chubakur/arcod/issues/55).
- **Успешный POST всегда 201**: идемпотентная досылка события возвращает ту же
  строку, но не может ответить 200 — клиент не отличит повтор от создания —
  [#56](https://github.com/chubakur/arcod/issues/56).

Осознанные ограничения примера:

- Объём: `io.find` без пагинации, снапшот читает до 4000 строк. Для реального
  каталога нужен батчевый обход и OLAP-агрегаты (#26).
- `recompute` пересобирает всего пользователя (до 60 товаров, 200 пар) — это
  осознанный дебаунс, а не инкрементальный апдейт.
- Товар не удаляется: `active: false` выкидывает его из снапшота, история
  остаётся.
