# 045 — Meeting scheduler (слоты, часовые пояса, приглашения)

Система записи на встречи для нескольких хостов: у каждого свои рабочие часы в
своём часовом поясе, гость просит свободные слоты в своём, бронь занимает
15-минутные ячейки календаря, а приглашение в формате `.ics` собирает фоновый
консьюмер и кладёт в S3. Напоминания выстреливают отдельным cron-хуком.

Статус: **partial** — весь поток работает, но исходящей почты в Arcod нет:
приглашение остаётся файлом в S3, а не письмом (см. «Чего не хватило»).

## Компоненты

```
                    HTTP
  guest/host ────────────────► Scheduler (arc, один сервис)
                                 │  Host / Booking / Hold / Invite / Reminder
                                 │
              ┌──────────────────┼───────────────────┬─────────────────┐
              ▼                  ▼                   ▼                 ▼
          Postgres            Redis              S3 (MinIO)          ids
       (rows, unique)     (queue: invite,      (.ics: invites/,   (uuid v4)
                           reminder)            reminders/)
                                 │
                                 ▼
                      consumers: deliver / remind
                      (build .ics → blobPut → mark sent)
```

| Компонент | Provider | Роль |
|---|---|---|
| `store` | `postgres` | хосты, брони, ячейки-холды, приглашения, напоминания |
| `events` | `redis` | очереди `invite` и `reminder`, ретраи, dead-letter |
| `files` | `s3` (MinIO) | объекты `invites/<booking>/invite.ics`, `cancel.ics`, `reminders/<booking>.ics` |
| `uuid` | `local` | идентификаторы строк и сообщений |

Внешние системы в `docker-compose`: **Postgres**, **Redis**, **MinIO** — три.

## Как устроено

**Слоты.** Рабочие часы хоста хранятся как `"09:00"`–`"17:00"` и трактуются в
его зоне. Поиск слотов идёт по UTC-сетке шагом 15 минут в пределах локальных
суток гостя; кандидат остаётся, только если в зоне хоста это будний день и
время внутри рабочих часов. Поэтому переход на летнее время ничего не ломает:
хранится инстант, а не настенное время.

**Бронь.** Каждая занятая 15-минутная ячейка — строка `Hold` с уникальным
ключом `hostId + ":" + ISO`. `insert` и есть compare-and-swap: второй гость на
ту же ячейку получает `409 Conflict`, частично вставленные холды откатываются
компенсацией. Отмена удаляет холды, и слот снова доступен.

**Приглашения.** `book` пишет `Invite` (`status: pending`) и публикует
`events.invite`; консьюмер `deliver` собирает `.ics`, кладёт в S3 и помечает
`sent`. Повторная доставка идемпотентна по статусу. Отмена создаёт второй
`Invite` (`kind: cancel`), и тот же консьюмер пишет `METHOD:CANCEL`.

**Напоминания.** На бронь создаётся `Reminder` с `dueAt = startsAt - 1h`.
`POST /v1/reminders/dispatch` — cron-хук: он только забирает созревшие строки и
публикует `events.reminder`, отправкой занимается консьюмер `remind`.
Повторный вызов ничего не дублирует.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/v1/hosts` | создать хоста (email уникален) |
| GET | `/v1/hosts/:hostId/slots?date=&tz=&dur=` | свободные слоты в зоне гостя |
| POST | `/v1/bookings` | забронировать слот (409 при пересечении) |
| GET | `/v1/bookings/:id` | бронь с локальным временем обеих сторон |
| POST | `/v1/bookings/:id/cancel` | отменить, освободить слот, отправить CANCEL |
| GET | `/v1/bookings/:id/invite` | ключ и содержимое `.ics` из S3 |
| POST | `/v1/reminders/dispatch` | cron-хук напоминаний |
| GET | `/v1/stats` | счётчики |

`startsAt` принимается и отдаётся в ISO-8601 UTC; `hostLocal`/`guestLocal` —
подписи вида `2026-12-01 11:00 Europe/Berlin`.

## Запуск

```bash
arcod check
arcod build --impl --port 8097
arcod run --impl --port 8097      # Postgres + Redis + MinIO + сервис
./smoke.sh                        # сборка, запуск, HTTP-проверки, PASS
arcod run --down --impl
```

`smoke.sh` проверяет: дубликат email → 409, неизвестная зона и перевёрнутые
часы → 400, слоты в зоне гостя (Berlin 09:00 = New York 03:00), закрытые
выходные, точное и частичное пересечение → 409, `.ics` в S3 и его `DTSTART`,
идемпотентность dispatch, освобождение слота после отмены, 404 на неизвестную
бронь и отсутствие dead-letter.

## Опыт использования Arc

Что понравилось:

- `unique` на ключе холда дал честную защиту от двойной брони без транзакций и
  блокировок: гонка двух гостей — это просто `Conflict` на `insert`.
- Три провайдера (`sql`, `queue`, `blob`) собираются в compose одной командой,
  включая MinIO и healthcheck'и; руками ничего поднимать не пришлось.
- Консьюмеры с `retry` и dead-letter работают: упавшее сообщение видно в логе
  (`attempt 1/4 failed ... moved to dead letter`), ошибка не теряется.
- Часовые пояса нормально живут в impl: `Intl` доступен, `datetime` — это ISO
  UTC, так что вся арифметика зон осталась в коде, а не в схеме.

Чего не хватило:

1. **Почты нет.** Capability `mail` убрали (issue #33), исходящего HTTP тоже нет:
   `net` можно только запретить, эффекта «вызвать внешний сервис» в капабилити
   нет. Поэтому приглашение — объект в S3, а не письмо. Для настоящей системы
   нужен `mail`/webhook-эффект; issue #60.
2. **Нет отложенных сообщений.** Напоминание «за час» нельзя положить в очередь
   с `at`, поэтому нужен внешний cron-хук (`/v1/reminders/dispatch`). Это
   открытый issue #12 про `at/after`.
3. **Тело job обязано вернуть значение.** Если консьюмер отработал и вернул
   `undefined`, рантайм считает это ошибкой: «consumer returned no result for
   its input», сообщение ретраится 4 раза и уходит в dead-letter, хотя работа
   уже сделана. В спеке у job нет возвращаемого типа, так что это неочевидно; issue #59.
4. **Нет CAS для `update`.** Dispatch помечает напоминание `queued` обычным
   `update`, поэтому два параллельных вызова могут отправить его дважды
   (консьюмер спасает идемпотентностью). Это открытый issue #58.
5. **Файл из S3 отдаётся JSON-полем.** `blob.get` возвращает строку в `body`,
   а не `text/calendar` байтами; для скачивания гостю нужен отдельный маршрут
   или поддержка файловых ответов (issue #53).

## Ограничения примера

- Один сервис; масштабирование консьюмеров не проверялось.
- Календарь хоста — только рабочие часы и брони в этой системе; внешние
  календари (Google/CalDAV) не подключены.
- Длительность — от 15 до 240 минут, кратная 15: сетка холдов фиксированная.
