# 037 — CI-оркестратор

Система запуска пайплайнов: описание шагов, очередь прогонов, фоновый
исполнитель, логи и артефакты в объектном хранилище, отмена и статистика.
HTTP-ответ на `trigger` не ждёт ни одного шага: он только фиксирует прогон и
отдаёт его в очередь.

Это не «сервис + kv». В работе участвуют **четыре внешние системы** (MySQL,
Redis-очередь, S3 и машина сборки за HTTP-endpoint) и **один фоновый
консьюмер**. Состояние прогона переживает рестарт сервиса: строки шагов — это и
есть журнал выполнения.

## Компоненты

```
   POST /v1/pipelines/:id/runs
              |
              v
      +---------------+     insert run + steprun      +------------------+
      | Orchestrator  | ----------------------------> |      MySQL       |
      |   (HTTP)      | <---------------------------- | pipelines/steps  |
      +-------+-------+        fetch / update        | runs / stepruns  |
              |                                      | artifacts        |
              | queuePublish('execute')              +------------------+
              v
      +---------------+      job execute(runId)       +------------------+
      | Redis queue   | ----------------------------> |  Orchestrator    |
      | execute topic |                               |  (consumer)      |
      +---------------+                               +----+--------+----+
                                                           |        |
                                       POST /execute       |        | blobPut
                                                           v        v
                                                  +-------------+ +-----------+
                                                  |   Runner    | |    S3     |
                                                  | (build box) | | logs/     |
                                                  +-------------+ | artifacts/|
                                                                  +-----------+
```

Шаги выполняются по возрастанию `position`. Первый ненулевой exit-код
останавливает пайплайн: текущий шаг `failed`, остальные `skipped`. Флаг
`cancelRequested` проверяется перед каждым шагом, поэтому отмена не рвёт
уже начатую команду, но следующая не стартует.

## Компонент → provider

| Компонент | Что хранит | Provider | Внешняя система |
|-----------|------------|----------|-----------------|
| `store` | пайплайны, шаги, прогоны, артефакты | `sql` | MySQL 8.4 |
| `jobs` | очередь `execute`, dead letter | `queue` | Redis 7 |
| `files` | логи шагов, артефакты сборки | `blob` | S3 (MinIO) |
| `Runner` | машина сборки | `endpoint` | внешний HTTP-сервис |
| `uuid` | идентификаторы | `ids` | локально |

## API

| Метод | Путь | Что делает |
|-------|------|-----------|
| POST | `/v1/pipelines` | создать пайплайн со списком шагов (201, 400, 409) |
| GET | `/v1/pipelines` | список пайплайнов |
| GET | `/v1/pipelines/:id` | пайплайн и его шаги (404) |
| POST | `/v1/pipelines/:id/runs` | запустить прогон (201, 404, 409 при активном) |
| GET | `/v1/pipelines/:id/runs` | история прогонов |
| GET | `/v1/runs/:id` | прогон и статусы шагов |
| POST | `/v1/runs/:id/cancel` | попросить отмену (200, 404, 409) |
| GET | `/v1/runs/:id/logs/:position` | лог шага из S3 |
| GET | `/v1/runs/:id/artifacts` | артефакты прогона |
| GET | `/v1/artifacts/:id` | содержимое артефакта |
| GET | `/v1/stats` | счётчики прогонов и артефактов |
| GET | `/v1/dead` | dead letter очереди `execute` |

## Запуск

```bash
arcod check
arcod build --impl --port 8095
arcod run --impl --port 8095      # http://localhost:8095
./smoke.sh                        # сборка, запуск, HTTP-проверки, PASS
arcod run --down --impl           # остановка
```

`smoke.sh` поднимает сервис, запускает mock машины сборки в сети compose под
именем `runner` и проходит сценарий: создание пайплайна, успешный прогон с
тремя шагами, лог и артефакт из S3, 409 на второй параллельный запуск, отмена
посреди медленного шага, падение шага с `skipped` у следующего, статистика,
404 и пустой dead letter.

## Опыт использования Arc

Что понравилось:

- `job execute(runId) { on: jobs.execute; retry: 1 }` — ровно та единица
  работы, которая нужна оркестратору. Строки `StepRun` пишутся до шага, так
  что повторная доставка продолжает с последнего незавершённого шага.
- `io.remote` не даёт зашивать адрес в модель: `Runner` объявлен как
  `external service`, адрес живёт в `environment dev`.
- `io.blobPut`/`io.blobGet` принимают строку и content-type: лог и
  артефакт — это байты в S3, а не поле в БД.
- Проверки `post`, `on error` и типы `int?` не дают забыть про 404/409.

Чего не хватило (issue — в `ISSUES.md`):

- `io.remote` возвращает `{ status, body }`, но сигнатура в подсказке этого
  не говорит: первый заход упал на `Number(reply.exitCode) = NaN` и MySQL
  получил `exitCode = NaN`. Обход — развернуть `body`; подробности в #32 и
  дубликате #45.
- У `sql` нет запросов с агрегатами/диапазонами: статистика считается
  `count` по статусу, а «последние N прогонов» — `find` с `order`. Для
  реального CI понадобится `group by` или `io.query`.
- Нет таймеров: «прогон завис дольше N минут → failed» не выразить без
  внешнего cron (issue #12).
- Отмена кооперативная: нельзя прервать уже отправленную команду (#46).
- POST всегда отвечает 201, поэтому `cancel` в smoke принимает и 200, и 201
  (#47).
