# 044 — Совместный редактор

Совместное редактирование текста: клиент присылает операции, сервер назначает
им порядок, живой канал раздаёт правки и курсоры всем открытым вкладкам, а
фоновый консьюмер сворачивает журнал операций в снимок в S3.

Это не «сервис + kv». В работе участвуют **три внешние системы** (MySQL,
Redis и S3/MinIO) плюс websocket-канал и **два фоновых консьюмера**
(`compact`, `notify`).

## Компоненты

```
 клиент A ──HTTP──┐                        ┌── MySQL: Doc, Op, Comment, Revision
 клиент B ──HTTP──┤   Docs (arc)           │
      ▲           ├─ sql ─────────────────┘
      │           ├─ blob ────────────────► S3/MinIO: docs/<id>/snapshot-<v>.json
      │  websocket├─ queue ───────────────► Redis: compact, notify
      └───────────┤                         │
        /ws?topic=└─ stream (websocket)     ├── job compact  → снимок + Revision
                                            └── job notify   → статус комментария
```

- **Docs** — единственный сервис, отдающий HTTP и websocket на одном порту.
- **MySQL** — метаданные документа, журнал операций (источник истины),
  комментарии, ревизии снимков.
- **Redis** — очередь заданий; в этом примере без `bind live -> redis`
  websocket работает в памяти одного процесса.
- **MinIO/S3** — тело снимка; в БД лежит только ключ.
- **job compact** — переигрывает Op-строки и пишет снимок; ставится на каждой
  20-й операции журнала, повторный запуск для той же версии ничего не пишет.
- **job notify** — переводит комментарий в `notified` и публикует событие.

## Компонент → provider

| Компонент | Capability | Provider |
|-----------|------------|----------|
| Документы, операции, комментарии, ревизии | `sql` | `mysql` (MySQL 8.4) |
| Очередь `compact`/`notify` | `queue` | `redis` (Redis 7) |
| Снимки документов | `blob` | `s3` (MinIO) |
| Живые операции и курсоры | `stream` | `websocket` (`/ws`) |
| Идентификаторы | `ids` | `local` (uuid v4) |

## API

| Метод | Путь | Что делает |
|-------|------|------------|
| POST | `/v1/docs` | создать документ (`title`, `owner`) → 201 |
| GET | `/v1/docs?limit=` | последние документы |
| GET | `/v1/docs/:id` | документ с текущим текстом и версией |
| POST | `/v1/docs/:id/ops` | применить операцию (`clientId`, `seq`, `kind`, `pos`, `text`) |
| GET | `/v1/docs/:id/ops?since=` | журнал после версии `since` |
| POST | `/v1/docs/:id/cursor` | опубликовать курсор, ответ — сколько сокетов получило |
| POST | `/v1/docs/:id/comments` | комментарий → строка + задание `notify` |
| GET | `/v1/docs/:id/comments` | комментарии и их статусы |
| POST | `/v1/docs/:id/snapshot` | явный снимок в S3 + ревизия |
| GET | `/v1/docs/:id/snapshot` | последний снимок из S3 |
| GET | `/v1/docs/:id/revisions` | история снимков |
| GET | `/v1/stats` | счётчики docs/ops/comments/revisions |
| GET | `/v1/dead` | недоставленные задания `compact`/`notify` |

Правила операций: `insert` вставляет `text` в позицию `pos`; `delete`
удаляет `text.length` символов (пустой `text` — один символ). Повтор с той же
парой `(clientId, seq)` возвращает `duplicate: true` и текст, переигранный из
лога. Пара объявлена как `unique Op.(docId, clientId, seq)`, поэтому
параллельный повтор либо получает `duplicate`, либо `409 Conflict`, но второй
строки в логе не появляется. 

## Запуск

```bash
cd 044-collab-editor
arcod check
arcod build --impl --port 8094
arcod run --impl --port 8094
./smoke.sh              # ждёт healthz, гоняет API, websocket и оба консьюмера
arcod run --down --impl # остановить
```

`smoke.sh` поднимает compose (MySQL, Redis, MinIO), ждёт `/healthz`, проверяет
создание, идемпотентный повтор, удаление, 400 на неизвестный `kind`, реальный
websocket-кадр, снимок из S3, оба фоновых задания, статистику, пустой
dead-letter и 404. В конце печатает `PASS`; контейнеры гасятся по `trap`.

## Опыт использования Arc

Как устроено: `Op` — append-only журнал, `Doc.content` и `Doc.version` не
материализуются, а пересчитываются на чтении (version — порядковый номер
строки в логе). Так пример переживает параллельные записи: 10 одновременных
операций дают version 10 и все 10 символов. До этого документ обновлялся
через `fetch` + `update`, и 10 параллельных операций давали version 2 и три
символа — см. issue #58.

Что легло хорошо:

- пять capability-алиасов в одном сервисе (`sql`, `queue`, `blob`, `stream`,
  `ids`) и два `job` с разными топиками — модель остаётся декларативной,
  а обработчики лежат в `impl/*.mjs`;
- `live.publish` возвращает число получателей: в smoke это дало честную
  проверку «курсор дошёл до открытого сокета» (`delivered: 1`), а не просто 200;
- составной `unique Op.(docId, clientId, seq)` работает и снимает гонку
  идемпотентных повторов: последовательный повтор отвечает `duplicate: true`,
  параллельный — либо `duplicate`, либо `409`, но второй строки не появляется;
- `A083` поймал на `check`, что `rabbitmq` нельзя биндить в `queue` (нет
  рантайм-драйвера) — переключение на `redis` заняло одну строку;
- `arcod providers` печатает примечание о провайдерах без рантайма, так что
  ловушка `rabbitmq`/`kafka` видна ещё до `check`.

Чего не хватило:

- **`sql.update` без предусловия** (issue
  [#58](https://github.com/chubakur/arcod/issues/58)): нет CAS/транзакции,
  поэтому материализованный `content`/`version` теряет обновления под
  параллелью. Пришлось сделать лог источником истины и пересчитывать текст на
  каждом чтении; для больших документов это дорого, и напрашивается
  `update(..., { if: { version: n } })`.
- **Возврат job-тела не виден из контракта.** `job`, который сделал работу и
  вернул `undefined`, попадает в dead-letter как
  `consumer returned no result for its input` — при этом побочные эффекты уже
  применены. Поведение описано в README, но в `main.arc` нет ни `returns`, ни
  предупреждения `check`: первый прогон дал «фантомное» письмо в dead-letter.
- **Приватные функции в `impl` делят один модуль**: два обработчика с локальным
  `replay()` падают на `build --impl` с `duplicate top-level name` (известно,
  #39). Текст ошибки называет файлы, но не подсказывает обходной путь.
- **Нет отложенного/дебаунс-запуска job**: компакция ставится из обработчика
  по счётчику «каждая 20-я операция». Для реального редактора нужен debounce
  по времени, а это ручной код в каждой операции.
- 13 предупреждений `W012` (нет примеров у операций) на новом примере: шум,
  который не мешает, но `check` в CI выглядит тревожно.
