# 040 — Feature store: online/offline консистентность

Хранилище признаков для ML: определения фич с версиями, приём наблюдений,
быстрое онлайн-чтение последнего значения, офлайн-история в объектном хранилище
и выгрузка обучающей выборки «на момент времени» с обогащением из внешнего
сервиса профилей.

Это система, а не «сервис + kv»: четыре внешние системы (MySQL, Redis, S3,
сервис профилей по HTTP), два фоновых консьюмера (материализация наблюдений и
сборка экспорта) и один поток наружу — вызов чужого HTTP-сервиса. Пять
capability: `sql`, `kv`, `queue`, `blob`, `ids` плюс `endpoint`.

## Компоненты и провайдеры

| Компонент | Capability → provider |
|-----------|-----------------------|
| Определения фич, версии, наблюдения, экспорты | `sql` → MySQL |
| Онлайн-значения `f:<feature>:<entity>` | `kv` → таблица `arcod_kv` в том же MySQL |
| Очереди `events` и `exports` | `queue` → Redis |
| Офлайн-объекты и CSV экспортов | `blob` → S3 (minio) |
| Атрибуты профиля (segment/country/plan) | `endpoint` → внешний HTTP-сервис |
| Идентификаторы | `ids` → local |

Почему онлайн-слой не в Redis: A094 запрещает держать `kv`-алиас на Redis,
когда сервис хранит данные в `sql` — «алиас жил бы в таблице `arcod_kv`
sql-хранилища». Так что kv-алиас `cache` объявлен без bind и живёт в MySQL;
см. «Опыт использования Arc».

## Схема

```
producer ──POST /v1/events──► mysql: Event (durable row)
                                   │
                                   │ очередь events
                                   v
                             job materialize ──► s3: offline/<feature>/<day>/<id>.json
                                   │
                                   └──────────► arcod_kv: f:<feature>:<entity>
                                                       ▲
клиент ──GET /v1/online/:feature/:entityId─────────────┘

клиент ──POST /v1/exports──► mysql: Export (queued)
                                   │
                                   │ очередь exports
                                   v
                             job buildExport ──► профили (HTTP)
                                   │
                                   └──► s3: exports/<id>.csv
```

Гарантии:

* строка наблюдения пишется **до** сообщения в очередь: потеря сообщения стоит
  повторной материализации, потеря строки — самого наблюдения;
* офлайн-объект пишется **до** онлайн-значения: кэш — проекция, а не источник
  истины;
* материализация не откатывает онлайн-значение назад по времени: поздно
  пришедшее старое наблюдение попадает в офлайн, но не перетирает свежее;
* экспорт — point-in-time: для каждой пары (сущность, фича) берётся последнее
  значение **не позже** `toAt`, всё после окна отбрасывается.

## API

| Метод и путь | Что делает |
|--------------|------------|
| `POST /v1/features` | завести фичу (v1); дубль → 409, неизвестный dtype → 400 |
| `GET /v1/features` | все определения |
| `POST /v1/features/:name/versions` | новая версия; старые события сохраняют старую |
| `POST /v1/events` | записать наблюдение и поставить материализацию в очередь |
| `GET /v1/online/:feature/:entityId` | последнее материализованное значение, `ageSeconds`, `stale` |
| `GET /v1/offline/:feature/:entityId` | история наблюдений из строк |
| `POST /v1/exports` | поставить сборку CSV в очередь |
| `GET /v1/exports/:id` | статус `queued`/`done`/`failed`, строки, ключ в S3 |
| `GET /v1/exports/:id/file` | `{ key, content }` — CSV из S3 |
| `GET /v1/stats` | фичи, события, pending, экспорты |
| `GET /v1/dead` | dead letter по обеим очередям |
| `POST /v1/dead/replay` | вернуть записи в очередь (status 200) |

`stale` считается по `ttlSeconds` фичи: значение старше бюджета помечается, но
не удаляется — в этом и смысл «честного» онлайн-слоя.

## Что проверяет smoke

1. Три фичи, дубль → 409, неизвестный dtype → 400, список из трёх.
2. Пять наблюдений, неизвестная фича → 404, нечисловое значение для `int` → 400,
   материализатор догоняет очередь (`pending = 0`).
3. Онлайн: значение 7, `stale = true` (наблюдение старше TTL), версия 1.
4. Позднее старое наблюдение не откатывает онлайн-значение.
5. Версия 2: новые события несут v2, офлайн хранит все четыре точки.
6. Экспорт: 3 строки, обрезка по `toAt` (событие после окна не попало),
   атрибуты профиля в CSV.
7. Dead letter: профиль отвечает 500 → джоб уходит в dead letter, экспорт
   `failed`; после `/heal` и `POST /v1/dead/replay` экспорт доходит до `done`,
   dead letter пуст.
8. Статистика: 3 фичи, 2 готовых экспорта, 0 pending.

## Опыт использования Arc

Что получилось без обходов:

* 12 операций и 2 джоба уложились в один `main.arc`; `check` ловил и типы
  (`value: string` + разбор по `dtype`), и эффекты (`bus.publish` без `allow`
  не проходит), и `post:`-условия;
* фоновые консьюмеры с `retry` и dead letter работают: упавший вызов профиля
  дал `attempts: 2` в dead letter, `queueDeadDrop` + повторная публикация
  довели экспорт до `done`;
* `status: 200` на `POST /v1/dead/replay` работает (после #47);
* один queue-алиас обслуживает два топика (`events`, `exports`) без второго
  брокера;
* `endpoint` + `host.docker.internal` доставляет вызов на хост (после #42).

Чего не хватило (issue заведены/проверены):

* **Онлайн-слой нельзя вынести в Redis.** A094: `bind cache -> redis` при
  `uses store: sql` — ошибка check; kv-алиас живёт в `arcod_kv` того же MySQL.
  Для feature store это принципиально: онлайн-нагрузка и метаданные делят одну
  БД. Обход: kv без bind (так и сделано), в README это названо прямо.
  Смежное — закрытый #37.
* **Контракт kv в impl не описан.** `cache.get/cache.set` в спеке
  соответствуют `io.load/io.save`, ключ получает жёсткий префикс `msg:`, а
  значение — конверт `{ b, h }`. Ни README, ни LSP этого не говорят:
  первая версия `online` читала `rec.value` и отдавала 404 при живом значении.
  Issue: `impl: контракт kv (io.load/io.save, {b,h}, префикс msg:) не описан`.
* **Нет способа отдать файл байтами.** `GET /v1/exports/:id/file` возвращает
  запись `{ key, content }` и `application/json`; CSV приходится разворачивать
  на клиенте. Issue: `contract: ответ файлом — только запись с content`.
* **OLAP-провайдер объявлен, адаптера нет** (#26, open): clickhouse поднимается,
  но `uses x: olap` не даёт эффектов. Поэтому офлайн-аналитика — S3 + `io.find`
  по строкам; на больших объёмах это не columnar.
* **`io.remote` возвращает `{ status, body }`**, а не тело (#32, закрыт как
  документация). В `buildExport` конверт разворачивается явно.
