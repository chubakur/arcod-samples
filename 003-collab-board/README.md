# 003 — Collab board

Совместная доска для фигур: несколько клиентов рисуют прямоугольники и двигают
их одновременно, сервер сливает правки без потерь. Это backend-пример: состояние,
журнал операций и websocket-рассылка, без UI.

Проект проверяет Arcod на задаче, где важна не форма запроса, а семантика
слияния: две правки разных полей одной фигуры не должны затирать друг друга,
а одинаковая правка одного поля должна разрешаться одинаково на всех репликах.

## Модель

`Room` — комната с монотонной `revision` (она же `seq` последней операции).

`Shape` — прямоугольник. У каждого изменяемого поля (`x`, `y`, `w`, `h`,
`color`) есть своя пара «часы + автор»: `xClock`/`xBy`, `yClock`/`yBy` и т.д.
Удаление — tombstones: `deleted`, `delClock`, `delBy`. Состояние фигуры не
теряет историю, поэтому запоздавшая правка не воскрешает удалённую фигуру.

`Op` — неизменяемый журнал: `seq`, `clientId`, `shapeId`, `kind`, `lamport`,
поля патча, `at`. Журнал нужен для догона после разрыва связи и для аудита.

### Правило слияния

Для каждого поля отдельно:

1. больший Lamport-счётчик побеждает;
2. при равных часах побеждает лексикографически больший `clientId`
   (детерминированный tie-break, а не «кто последний пришёл»);
3. правки разных полей не конфликтуют вообще — это и есть «без потерь».

Операция идемпотентна по `opId`: повтор после потерянного ответа возвращает
сохранённую операцию с `duplicate: true` и не применяет патч второй раз.

## API

| Метод | Путь | Что делает |
|-------|------|------------|
| POST | `/v1/rooms` | создать комнату |
| GET | `/v1/rooms` | список комнат (`limit`, по умолчанию 50) |
| GET | `/v1/rooms/:id` | комната по id |
| POST | `/v1/rooms/:roomId/ops` | применить операцию |
| GET | `/v1/rooms/:roomId/board` | снимок: живые фигуры и `revision` |
| GET | `/v1/rooms/:roomId/ops?after=0&limit=200` | журнал после `seq` |
| WS | `/ws?topic=room:<roomId>` | поток `{"type":"op","revision":N,"op":{...}}` |

Тело операции — плоский JSON:

```json
{
  "opId": "00000000-0000-4000-8000-000000000101",
  "clientId": "alice",
  "shapeId": "00000000-0000-4000-8000-000000000001",
  "kind": "add",
  "lamport": 1,
  "x": 10, "y": 20, "w": 100, "h": 50,
  "color": "#ff0000"
}
```

`kind`: `add` (нужны все геометрические поля), `update` (любое подмножество
`x/y/w/h/color`), `delete`. Ответ: `{op, revision, duplicate}`.

Ошибки объявлены в контракте: неизвестная комната — `404 NotFound`,
неизвестная фигура или кривые поля — `400 Invalid`, а не 500.

## Запуск

Нужны Node.js >= 22.18, Docker и `arcod` из `chubakur/arcod`.

```bash
cd 003-collab-board
arcod check
arcod build --impl
arcod run --impl --port 8096
```

Проверка целиком (сборка, старт, слияние, websocket, остановка):

```bash
./smoke.sh
# или без глобального arcod:
ARCOD=/path/to/arcod/bin/arcod.mjs ./smoke.sh
```

Smoke оставляет стек запущенным только на время теста и в конце делает
`arcod run --down --impl`. Остановить вручную:

```bash
arcod run --down --impl
```

## Что проверяет smoke

1. комната создаётся с `revision = 0`;
2. `alice` двигает `x`, `zoe` одновременно двигает `y` — на доске оба значения;
3. обе пишут `color` на одном Lamport — побеждает `zoe` (tie-break по clientId);
4. старая правка `x=99` не затирает `x=30`;
5. повтор `opId` возвращает `duplicate: true` и не двигает `revision`;
6. websocket-подписчик получает следующую операцию;
7. `delete` убирает фигуру с доски, но операция остаётся в журнале;
8. `GET /ops?after=6` отдаёт ровно две операции, неизвестная комната — 404,
   неизвестная фигура — 400.

## Опыт использования Arc

Что понравилось:

- `list<Shape>`, вложенные записи и опциональные поля в операции описали
  контракт без ручных JSON-схем; `arcod check` поймал размещение `examples`
  вне сервиса сразу.
- `build --impl` дал рабочий HTTP-сервис, Dockerfile и compose без ручной
  обвязки; `run --down` теперь действительно останавливает стек и не чистит
  `.arcod/build` (проверено на чистом checkout).
- Websocket-поток (`bind stream -> websocket()`, `io.publish`) заработал с
  первого раза: один порт, путь `/ws?topic=...`, текстовые кадры. Подписка на
  `room:<id>` из `node`-клиента прошла без библиотек.
- Идемпотентность и tombstones хорошо ложатся на типы: `deleted`, `delClock`,
  `delBy` — часть контракта, а не скрытое поле в блобе.

Чего не хватило:

- **SQL-провайдер не работает для списков.** Первая версия была на
  `store: sql`; `io.find` падает с `TypeError: q is not a function`
  (затенение хелпера в сгенерированном `SqlStore.entityFind`). Пришлось
  перейти на `kv`. Issue: [#9](https://github.com/chubakur/arcod/issues/9).
- **Нет CAS/атомарного счётчика для kv.** `seq` и проверка дубля — это
  read-modify-write из нескольких вызовов; при параллельных запросах два
  клиента могут получить один `seq`, а два ретрая — вставить один `opId`.
  Сейчас пример честно рассчитан на один инстанс и последовательные записи;
  под нагрузкой нужен `updateIf`/атомарный `incr` или транзакция.
  Issue: [#10](https://github.com/chubakur/arcod/issues/10).
- **Компакция журнала.** Журнал растёт вечно; для настоящей доски нужен
  снапшот + обрезка `Op` до `snapshotSeq`, но в языке нет транзакционного
  «удалить пачку и записать снапшот». Пока журнал читается страницами.
- **Присутствие и курсоры.** `stream` — рассылка, но нет серверного списка
  подключённых клиентов; presence пришлось бы строить отдельными операциями.
- **Атомарность seq на нескольких репликах.** Даже с CAS по `Room.revision`
  нужен общий брокер для `stream` (`bind stream -> redis(...)`), иначе
  websocket-подписчики на другой реплике не увидят операцию. В примере
  `websocket()` — один инстанс.

## Ограничения примера

- Нет аутентификации: `clientId` — заявленный клиентом, а не проверенный.
- Нет UI; смотреть доску можно через `curl`/jq, websocket — любым клиентом.
- `GET /ops` отдаёт страницу максимум 500; для полного догона клиент
  повторяет запрос с последним `seq`.
- Координаты и размеры — целые; углы, повороты, z-order и вложенность не
  моделируются.
