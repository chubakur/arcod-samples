# 039 — IoT-телеметрия: устройства, правила, алерты

Платформа приёма телеметрии: устройства шлют пачки показаний, пороговые правила
превращают их в алерты, дежурный сервис получает уведомление по HTTP, а суточный
срез показаний собирается фоновым джобом в объектное хранилище.

Это не «сервис + kv»: в системе четыре внешние системы (MySQL, Redis, S3, внешний
pager), два фоновых консьюмера (оценка показаний и сборка отчёта) и один поток
данных наружу (HTTP-вызов дежурного сервиса).

## Компоненты и провайдеры

| Компонент | Provider |
|-----------|----------|
| Реестр устройств, правила, алерты, отчёты, история показаний | `sql` → `mysql` 8 |
| Очередь `samples` и `reports` | `queue` → `redis` 7 |
| CSV-отчёт | `blob` → `s3` (minio) |
| Дежурный сервис (pager) | внешний `endpoint` → `http://host.docker.internal:9096` |
| Идентификаторы | `ids` → `local` |

`arcod build` генерирует `docker-compose.yml` в `.arcod/build/` — там четыре
контейнера: `mysql`, `redis`, `s3` (minio) и `service`. Pager в compose не входит:
это чужая система, в smoke её изображает маленький node-сервер.

## Схема

```
gateway ──POST /v1/devices/:id/readings──┐
                                        v
                              mysql: Reading (durable)
                                        |
                                        v  очередь samples
                                  job evaluate
                                   /          \
                         mysql: Alert     Pager (HTTP)
                              ^                |
                     ack/resolve        503 → retry 2 → dead letter

POST /v1/reports ── очередь reports ── job buildReport ── s3: reports/<id>.csv
```

Порядок важен: пачка показаний сначала пишется в MySQL (одна строка на sample),
и только потом публикуется сообщение. Потеря сообщения теряет оценку, но не
данные. Оценка идёт по каждой строке отдельно — так правило с `cooldownSec`
открывает один алерт на серию нарушений, а не на каждое показание.

## API

| Метод и путь | Что делает |
|--------------|------------|
| `POST /v1/devices` | зарегистрировать устройство; повтор `(name, site)` → 409 |
| `GET /v1/devices` | список устройств с `lastSeenAt` |
| `POST /v1/devices/:id/readings` | пачка показаний (до 100); 404 на неизвестное устройство |
| `GET /v1/devices/:id/readings?metric=&limit=` | история, новые сверху |
| `POST /v1/rules` | правило: `metric`, `op` (`gt`/`lt`), `threshold`, `cooldownSec`, `severity`, `deviceId` (по умолчанию `*`) |
| `GET /v1/rules` | правила |
| `GET /v1/alerts?status=open|all&limit=` | алерты, по умолчанию открытые |
| `POST /v1/alerts/:id/ack` | взять в работу (200, `acked`) |
| `POST /v1/alerts/:id/resolve` | закрыть (200, `resolved`); повтор → 409 |
| `POST /v1/reports` | поставить сборку CSV в очередь |
| `GET /v1/reports/:id` | статус `queued`/`ready` и счётчики |
| `GET /v1/reports/:id/file` | содержимое CSV из S3 |
| `GET /v1/stats` | устройства, показания, правила, открытые алерты |
| `GET /v1/dead` | содержимое dead letter по обоим топикам |
| `POST /v1/dead/drop` | снять разобранную запись (payload как напечатал `/v1/dead`) |

## Запуск

```bash
arcod check
arcod build --impl --port 8096
arcod run --impl --port 8096
./smoke.sh          # сам поднимает sink, стек и прогоняет все пути
arcod run --down --impl
```

`smoke.sh` заканчивается `PASS`. Он проверяет: регистрацию и 409, три правила,
пачку из трёх показаний, два открытых алерта (device-rule и wildcard-rule),
два вызова pager, порядок истории, `ack`/`resolve` с кодами 200 и 409,
cooldown, счётчики, отчёт `queued → ready` с CSV в S3 и dead letter после
503 от pager с последующим `drop`.

## Опыт использования Arc

Что язык дал сразу:

- четыре провайдера и два фоновых джоба — без единой строки инфраструктурного кода;
  `bind` в `environment` и `arcod build` сами собрали compose и миграции;
- `status: 200` на `POST` для `ack`/`resolve` — идемпотентные действия больше не
  притворяются созданием ресурса (было issue #47);
- `queueDeadDrop` в `POST /v1/dead/drop` — dead letter можно разобрать и снять
  (было issue #49);
- `decimal` для показаний дошёл до `DECIMAL(30,6)` и до JSON-схемы без ручных
  конверсий на границе;
- внешний сервис описан двумя типами и одним `op`; адрес живёт в `environment`,
  в теле — только `io.Pager.notify(...)`.

Чего не хватило (issues заведены отдельно):

- **нет `olap`/`stream`**: провайдеры `clickhouse` и `kafka` в таблице есть, но
  адаптера под них нет (`A083`-подобный отказ), поэтому история показаний лежит
  в MySQL, а «аналитика» — это джоб, читающий строки;
- **`rabbitmq` не может обслуживать `queue` в рантайме**: `arcod check` отвечает
  `A083 provider rabbitmq cannot serve queue at runtime`, приходится брать Redis;
- **нет отложенных сообщений и шедулера**: эскалация «алерт открыт N минут —
  звони» не реализована, только мгновенное уведомление; в README и issue;
- **impl-файлы склеиваются в один модуль**: две константы `OPS` в разных файлах
  дают `duplicate top-level name`, обходим префиксами `RULE_OPS`/`EVAL_OPS` (#39);
- **cooldown приходится хранить в строке правила** (`lastAlertAt`): нет способа
  спросить «когда последний раз срабатывало» у очереди или кэша.

## Ограничения примера

- один wildcard-уровень (`deviceId: "*"`); иерархии site/group нет;
- отчёт собирается по всем показаниям (лимит 5000 строк), без окон по времени;
- эскалация и повторное уведомление по таймеру не сделаны — см. выше;
- CSV без экранирования запятых в metric: имена метрик ограничены валидацией.

## Ссылки на issue

- **#26** — нет адаптера olap/stream: строка "uses x: olap" проходит check, а
  работать нечем. Поэтому история показаний в MySQL.
- **#30** — rabbitmq не может обслуживать queue: bind на rabbitmq падает в
  check с A083, пример берёт Redis.
- **#12** — нет отложенных сообщений: эскалация по времени не реализована.
- **#47** (fixed 24.11) — POST теперь умеет status: 200, используется в
  ack/resolve.
- **#49** (fixed 24.11) — queueDeadDrop снимает разобранную запись dead letter,
  используется в /v1/dead/drop.
- **#39** — impl-файлы склеиваются в один модуль, константы пришлось
  префиксовать (RULE_OPS/EVAL_OPS).

Внешний сервис вызывается только через "io.remote('Pager', 'notify', payload)"
и возвращает { status, body }; вариант "io.Pager.notify(...)" молча не сработал,
это нигде не описано — смотрел 011-metric-lake.
