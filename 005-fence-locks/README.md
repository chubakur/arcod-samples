# 005 — Fence locks

Сервис распределённых аренд: клиент берёт именованную блокировку на время,
продлевает её, отдаёт и получает **fencing token** — номер, который только
растёт. Ресурс, который помнит этот номер, отвергает запоздавшего держателя:
тот, кто «завис» и потерял аренду, физически не может перезаписать чужие
данные.

Это backend-пример: HTTP API, модель, Redis и e2e-проверка. UI нет.

## Зачем

Классическая ошибка «блокировка через ~~~SETNX~~~ + ~~~DEL~~~» ломается на паузе
держателя: GC, сетевой разрыв, засыпавший процесс — аренда истекла, новый
клиент её взял, а старый проснулся и пишет. Fencing token превращает «кто
первый» в «чей номер больше»: ресурс хранит последний применённый номер и
отказывает всему, что меньше.

В примере три роли:

1. **Аренда.** Один владелец на имя, TTL, продление только по токену.
2. **Fencing.** Номер выдаётся из журнала аллокаций; номер не переиспользуется
   даже после release.
3. **Guard.** Демонстрационный ресурс, который принимает запись только с
   номером не ниже последнего применённого.

## Модель

~~~arcod
type Lease = {
  id: LockId, name: string, owner: string, token: string,
  fence: int, ttlMs: int, renewals: int,
  acquiredAt: datetime, renewedAt: datetime, expiresAt: datetime
}

type Fence = {                 // журнал аллокаций, не аудит
  id: uuid, name: string, slot: string, fence: int, owner: string, at: datetime
}

type Trace = {                 // аудит: acquired | released | expired
  id: uuid, name: string, fence: int, kind: string, owner: string, at: datetime
}

type Guarded = {
  id: ResourceId, resource: ResourceId, fence: int,
  value: string, writer: string, writes: int, appliedAt: datetime
}
~~~

Три решения, без которых пример не работает:

- **Номер выдаёт вставка, а не чтение.** У ~Fence~ есть синтетическое поле
  ~slot = "<name>#<номер>"~ и ~unique Fence.slot~. «Взять следующий номер» —
  это ~insert~, который либо выигрывает claim, либо падает ~Conflict~.
  Read-modify-write счётчика здесь невозможен: в kv нет CAS
  ([#10](https://github.com/chubakur/arcod/issues/10)). Побочный эффект:
  номера могут идти с пропусками, но никогда назад.
- **Один держатель — это ~unique Lease.name~.** Проверка «живой аренды нет»
  и вставка не атомарны, поэтому решает claim при вставке: проигравший
  получает 409, а не вторую аренду.
- **Просрочку снимают по id, а не по имени.** Конкурент, который уже заменил
  запись, не будет удалён нашей поздней уборкой; ~remove~ по id — no-op.

## API

| Метод | Путь | Что делает |
|-------|------|-----------|
| POST | ~/v1/locks/:name/acquire~ | взять аренду; 409, если держат |
| POST | ~/v1/locks/acquire~ | взять набор имён целиком или ничего |
| POST | ~/v1/locks/:name/renew~ | продлить по токену |
| POST | ~/v1/locks/:name/release~ | отдать досрочно |
| GET | ~/v1/locks/:name~ | кто держит, номер, TTL |
| GET | ~/v1/locks?prefix=&limit=~ | живые аренды, ближайший дедлайн первым |
| GET | ~/v1/locks/:name/history~ | аудит: acquired / released / expired |
| POST | ~/v1/resources/:resource/write~ | запись под fence; старый номер — 409 |

Имя блокировки — путь, поэтому ~orders/42~ в URL выглядит как
~orders%2F42~. Токен отдаётся только в ответе ~acquire~; ~GET~ его не
показывает.

~~~bash
curl -s -X POST localhost:8098/v1/locks/orders%2F42/acquire \
  -H 'content-type: application/json' -d '{"owner":"worker-a","ttlMs":30000}'
# {"token":"…","lease":{"fence":1,…}}

curl -s -X POST localhost:8098/v1/resources/ledger/write \
  -H 'content-type: application/json' -d '{"fence":1,"value":"v1"}'
# 201; повтор с fence 1 и тем же value — replay, другой value — 409
~~~

## Запуск

~~~bash
arcod check                 # модель и предупреждения
arcod test                  # 5 example-сценариев из main.arc
arcod build --impl          # генерация .arcod/build
arcod run --impl --port 8098
./smoke.sh                  # сборка + запуск + HTTP-проверки, в конце PASS
arcod run --down --impl
~~~

## Что проверяет smoke

1. Второй владелец получает 409, а состояние не показывает токен.
2. Продление без токена — 403, с токеном — ~renewals~ растёт, окно сдвигается.
3. Повтор записи с тем же fence и тем же значением — replay; с другим
   значением — 409.
4. После release новый владелец получает fence 2, старый не может ни
   release, ни write.
5. Истёкшая аренда перестаёт держаться без фонового уборщика; её бывший
   владелец не может продлить (403) и не может записать (409).
6. Шесть одновременных acquire на одно имя — ровно один 201 и одна запись
   ~acquired~ в истории.
7. Набор из двух имён берётся в каноническом порядке; частичный набор
   откатывается и не оставляет «висящих» аренд.
8. Плохой ввод (ttl 10 мс, пустой owner, пустой набор, limit=0) — 400.

## Опыт использования Arc

- **~unique~ работает как CAS, если придумать поле.** Составного ключа в
  правилах нет, поэтому появилось синтетическое ~Fence.slot~. Это не хак ради
  хака: claim на вставке — единственная атомарная операция, доступная телу,
  и она честно ложится на fencing-номер. Отдельный issue —
  [составной unique](https://github.com/chubakur/arcod/issues/13).
- **~list<string>~ в examples наконец парсится.** Сценарий
  ~acquireAll(["orders/2","orders/1"])~ — прямая проверка закрытого
  [#3](https://github.com/chubakur/arcod/issues/3); на чистом состоянии
  воспроизвести старую ошибку не удалось, ~arcod test~ зелёный.
- **Тела операций делят один модуль** ([#11](https://github.com/chubakur/arcod/issues/11)):
  ~acquire~ и ~acquireAll~ не могут импортировать общий helper, поэтому
  логика аренды продублирована (~80 строк). В примере это видно как
  ~flTake~ и ~faTake~.
- **Ошибка не несёт данных.** 409 от ~acquire~ говорит только «conflict»:
  клиент не узнает текущий fence, владельца и ~expiresAt~, хотя сервис их
  знает. Пришлось делать отдельный ~GET~ — это лишний round-trip и гонка
  между двумя запросами. Issue — [payload ошибки](https://github.com/chubakur/arcod/issues/14).
- **Таймеров с ~at/after~ нет** ([#12](https://github.com/chubakur/arcod/issues/12)):
  фоновый sweeper не написать, поэтому просрочка снимается лениво — при
  чтении, продлении и захвате. Для аренд это даже честнее (нет «часов»,
  которые надо синхронизировать), но список живых аренд зависит от того,
  что кто-то их читал.
- **Проверки контракта приятны:** ~on error Conflict: name != null~ поймал
  опечатку в параметре до генерации. ~arcod test~ прогоняет примеры против
  настоящего хранилища и поймал ошибку в правиле replay (равный fence с
  другим значением), которую smoke бы пропустил.

## Чего не хватило

- **Составной unique** — ~unique Fence.(name, fence)~ вместо поля ~slot~.
  ([#13](https://github.com/chubakur/arcod/issues/13))
- **Тело ошибки** — вернуть текущий fence и ~expiresAt~ в 409, чтобы клиент
  знал, сколько ждать и какой номер бить. ([#14](https://github.com/chubakur/arcod/issues/14))
- **Атомарный примитив в теле** — ~store.claim(key)~ / ~insertIfAbsent~ вместо
  уникального поля-обманки. ([#10](https://github.com/chubakur/arcod/issues/10))
- **Отложенный запуск** для sweeper'а аренд. ([#12](https://github.com/chubakur/arcod/issues/12))
- **Общий модуль тел** — сейчас любая общая функция обязана быть продублирована
  с уникальным именем. ([#11](https://github.com/chubakur/arcod/issues/11))

## Ограничения примера

- Guard-ресурс читает и пишет двумя шагами: это демонстрация правила, а не
  транзакция. Настоящий ресурс делает сравнение у себя в хранилище.
- «Продлить, пока держишь» не поддерживает блокирующее ожидание: клиент
  опрашивает сам. Без ~at/after~ long-poll не построить.
- Часы — системные на сервисе; drift между узлами не компенсируется.
