# 015 — GDPR-стирание

Система исполнения запросов на удаление персональных данных: адрес субъекта
превращается в соль-хеш, каскад удаляет его строки в трёх CRM-таблицах, манифест
уезжает в S3, а внешний комплаенс-шлюз выдаёт юридический сертификат. Удаление и
сертификат — две разные очереди и два разных консьюмера: падение шлюза не делает
удаление ложью.

```
  client
    │  POST /v1/requests {subjectEmail, reason}
    ▼
┌──────────────────────────── Erasure (http, node) ───────────────────────────┐
│  create: hash(email) → ErasureRequest(state=pending) → events.erase          │
│  show/requests/subject/stats/retry/sweep: чтение и операторские действия     │
└───────────────┬──────────────────────────────────────────────┬──────────────┘
                │ queue: events.erase                          │ events.erased
                ▼                                              ▼
      job erase (consumer 1)                          job certify (consumer 2)
      mysql: Customer, OrderNote,                     external compliance gateway
             SupportTicket ← delete by subjectHash     POST /v1/certificates
      mysql: AuditEntry (manifest + resume marker)     → certificate → state
      s3: erasure/<id>/manifest.json                          = certified
```

Компоненты, которые видит клиент: создать запрос, посмотреть статус и манифест,
скачать сертификат-манифест, проверить остаток PII по адресу, повторить
застрявшее задание, подмести зависшие запросы.

## Компонент → provider

| Компонент | Capability | Provider | Зачем |
|-----------|-----------|----------|-------|
| Контрольные записи, CRM-таблицы, аудит | `store: sql` | `mysql:8.4` | транзакционные строки и каскад по индексу `subjectHash` |
| Очередь `events` (`erase`, `erased`) | `events: queue` | `redis:7` | at-least-once доставка двум консьюмерам |
| Манифест и доказательство | `files: blob` | `minio` (S3) | манифест переживает ретеншн БД; бакет не публичный |
| Комплаенс-шлюз | `Compliance: endpoint` | внешний HTTP | чужая система, знаем только контракт и адрес |
| Идентификаторы | `uuid: ids` | `local` | id запросов, клиентов, строк аудита |

Внешних систем четыре: MySQL, Redis, S3 (MinIO) и комплаенс-шлюз (мок в
`mock/compliance.mjs`).

## API

| Метод | Путь | Что делает |
|-------|------|-----------|
| POST | `/v1/requests` | создать запрос; 400 на плохой адрес, 409 если у субъекта уже есть живой запрос |
| GET | `/v1/requests?limit=` | последние запросы |
| GET | `/v1/requests/:id` | запрос + манифест из аудита + живой остаток PII |
| GET | `/v1/requests/:id/certificate` | манифест из S3 как файл |
| GET | `/v1/subjects/:subjectEmail` | остаток строк по таблицам и число запросов субъекта |
| POST | `/v1/requests/:id/retry` | переотправить `erase`/`erased`; 409 пока идёт каскад |
| POST | `/v1/sweep` | переотправить `erasing` старше 5 мин и `erased` без сертификата старше 2 мин |
| GET | `/v1/stats` | счётчики по состояниям и число удалённых строк |
| POST | `/v1/dev/seed` | демо-PII: alice (5 строк) и bob (3 строки) |

Состояния: `pending → erasing → erased → certified`; `failed` — только через
операторский `retry`.

## Запуск

```bash
cd 015-gdpr-erasure
arcod check
arcod build --impl
arcod run --impl --port 8096          # mysql + redis + minio поднимаются сами
PORT=9097 FAIL_FIRST=1 node mock/compliance.mjs &   # внешний шлюз
./smoke.sh                            # сборка, запуск, HTTP-проверки, PASS
arcod run --down --impl               # остановка (или docker compose down -v)
```

Если глобальный `arcod` старее репозитория, smoke умеет взять свежий бинарь:
`ARCOD_JS=/path/to/arcod/bin/arcod.mjs ./smoke.sh`.

## Опыт использования Arc

Что легло хорошо:

- `external service Compliance : http { contract { op certify(...) } }` — ровно та
  степень свободы, которая нужна чужой системе: контракт и адрес, без реализации.
  `bind Compliance -> endpoint(url: ...)` + мок на localhost, и консьюмер честно
  ходит по HTTP (retry виден по двум записям в логе шлюза).
- Два `job` на одно событие-продолжение (`erase` → `erased` → `certify`) —
  разделение «данные удалены» и «бумага получена» выражено самой моделью, а не
  комментарием в коде.
- `blobGet` в операции отдаёт байты клиенту: манифест лежит в S3, но наружу
  торчит только через сервис.
- `io.remove('Customer', id)` в цикле по `io.find(..., {where:{subjectHash}})` —
  каскад по трём таблицам пишется без SQL и без ORM.

Чего не хватило (issue заведены):

- **#38** — операция с именем `request` роняет сгенерированный сервис:
  `SyntaxError: Identifier 'handleRequest' has already been declared`. `check`
  молчит, `build --impl` зелёный, падает только запуск. Пришлось переименовать
  операцию в `show`. Нужен либо префикс у внутренних функций, либо ошибка на
  `check` для зарезервированных имён.
- **#39** — impl-файлы склеиваются в один модуль, и одинаковое имя функции в двух
  файлах даёт `duplicate top-level name "subjectHash"` только на `build --impl`.
  Хочется либо `import`/общего `lib.mjs`, либо подсказки на `check` (сейчас
  приходится дублировать хеш-функцию с разными именами).
- **#34** (открыт) — `io.aggregate` нет, поэтому «сколько всего удалено» считается
  вычиткой строк запросов в `stats`. Для отчёта по стиранию это терпимо, для
  денег — нет.
- **#37** (открыт) — `kv` не используется намеренно: `io.save/load` пишут в SQL,
  а не в Redis. Прогресс каскада пришлось хранить в `AuditEntry`, и это оказалось
  лучше: аудит и есть состояние возобновления.

Решения, которые стоит повторить:

- Хеш адреса с солью считается в impl, потому что в песочнице нет `node:crypto`.
  Для демо это FNV-1a; в реальной системе хеширует CRM-владелец адреса.
- Idempotency каскада — не «dedupe-ключ», а строка аудита на датасет: повторная
  доставка сообщения пропускает уже удалённые таблицы, а не пересчитывает их.
- `sweep` смотрит на возраст `updatedAt`, а не на «зависло/не зависло»: у
  очереди нет способа рассказать про потерянное сообщение.

## Проверки

`smoke.sh` (последний прогон — чистое состояние, arcod `f0119d3`):

1. health: сервис + mysql + redis + minio + мок шлюза;
2. seed: alice 5 строк, bob 3 строки;
3. повторный запрос по тому же субъекту → 409, адрес в ответе замаскирован;
4. каскад: 5 строк по трём таблицам, состояние `certified`;
5. изоляция: у bob по-прежнему 3 строки;
6. манифест из S3 отдаётся через API и сходится по строкам;
7. шлюз получил ровно два вызова: 503 (намеренный отказ) и 200 — ретрай доказан;
8. повторный `retry` сертифицированного запроса не звонит в шлюз; `sweep` пуст;
9. 400 на плохой адрес, 404 на неизвестный id, `stats.rowsErased = 5`.
